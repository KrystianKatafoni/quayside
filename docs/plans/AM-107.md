# AM-107 · core:storage: JsonStore (zapis atomowy, migracje, *.broken)

Issue: #15 · Wymagania: docs/11 §8, docs/12 (`JsonStore`) · Etap: M1

## Zakres

Moduł `core:storage` do trwałego zapisu plików konfiguracji (`projects.json`, `theme.json`, …):

- `JsonStore<T>`: `load()`, `save(value)`, `update(change)`. Wszystkie operacje jednego magazynu są serializowane przez `Mutex`, więc równoległe `update` nie gubią zmian.
- Format pliku: `{"schemaVersion": N, "data": <wartość>}`.
- Zapis atomowy: `<nazwa>.tmp` → `force(true)` → `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`.
- Migracje `vN → vN+1` (`Migration(fromVersion) { JsonObject -> JsonObject }`). Plik ze starszą wersją jest migrowany krok po kroku i od razu zapisywany w bieżącej wersji.
- Plik nie do odczytania (niepoprawny UTF-8, zły JSON, brak `schemaVersion`/`data`, wersja < 1, dane niepasujące do typu, nieudana migracja) jest przenoszony do `<nazwa>.broken`. Powód to stała kategoria (`invalid JSON`, `data does not match type`, …), bo komunikaty parsera cytują treść pliku, a ta nie może trafić do logów (ENG-C8). `load()` zwraca wtedy wartość domyślną z `Loaded.recovered`, żeby UI mogło pokazać komunikat.
- Plik z **nowszej** wersji schematu → `StorageError.NewerSchema`, plik zostaje nietknięty (bez cichego downgrade'u). Wersję sprawdzamy przed resztą koperty, więc przyszły format też nie jest przenoszony.
- Błędy IO → `StorageError.IoFailed(path, reason)`; nieudany zapis usuwa `.tmp`.
- Fabryka `JsonStorage(directory, io, logger).store(spec)`. `testFixtures`: `InMemoryJsonStore` (fake z symulacją `failure` i `recoverNextLoad`, ENG-I7) i `JsonStoreContract` (ENG-T2).

Nie robimy: obserwowania zmian pliku z zewnątrz, cache'u w pamięci, `StateFlow` (to zadanie modułów-właścicieli), lokalizacji katalogu Application Support (AM-108).

## Moduły

`core:storage` (nowy), `settings.gradle.kts`, `gradle/libs.versions.toml` (`kotlinx-serialization-json` 1.11.0).

Plugin `am.feature.api`. Kod produkcyjny nie potrzebuje pluginu kompilatora serializacji: używa `KSerializer<T>` podanego przez właściciela pliku. Testy korzystają z wbudowanych serializerów (`String`, `Map`).

## Zmiany API

Pakiet `dev.agentmanager.core.storage`:

```kotlin
interface JsonStore<T> {
    suspend fun load(): Outcome<Loaded<T>, StorageError>
    suspend fun save(value: T): Outcome<Unit, StorageError>
    suspend fun update(change: (T) -> T): Outcome<T, StorageError>
}
data class Loaded<out T>(val value: T, val recovered: BrokenFile? = null)
data class BrokenFile(val movedTo: Path, val reason: String)
sealed interface StorageError { NewerSchema(found, supported); IoFailed(path, reason) }
class Migration(val fromVersion: Int, val migrate: (JsonObject) -> JsonObject)
class StoreSpec<T>(fileName, serializer: KSerializer<T>, default: T, schemaVersion = 1, migrations = emptyList())
class JsonStorage(directory: Path, io: CoroutineDispatcher, logger: Logger = NoOpLogger) { fun <T> store(spec): JsonStore<T> }
```

`KSerializer` i `JsonObject` są w API świadomie: `core:storage` jest modułem infrastruktury, a nie `api` feature, więc ENG-I8 go nie obejmuje. Biblioteka jest wybrana w docs/11 §12, dlatego nie ma nowego ADR. Moduły `feature:*:api` nadal nie widzą tych typów; korzystają z nich tylko moduły `impl`.

## Ryzyka i pytania

- Dwa magazyny na ten sam plik nie są serializowane między sobą. KDoc `JsonStorage.store` mówi, żeby tworzyć jeden magazyn na plik (każdy plik ma jednego właściciela, docs/11 §8).
- `ATOMIC_MOVE` jest atomowy w obrębie jednego systemu plików; `.tmp` leży obok pliku docelowego, więc to spełnione.
- Kolejne uszkodzenie nadpisuje poprzedni `.broken` (zostaje tylko ostatnia kopia).
- `update` na uszkodzonym pliku odzyskuje go jak `load`, ale `BrokenFile` trafia tylko do logu — właściciel woła najpierw `load` (KDoc).
- Brak fsync katalogu po `ATOMIC_MOVE`: rename jest atomowy, ale po awarii zasilania może przepaść ostatni zapis (stary plik zostaje spójny).
- `docs/11` §9 pokazuje `JsonStorage(appSupportDir())`; konstruktor wymaga też `io` — do uwzględnienia w AM-108.
