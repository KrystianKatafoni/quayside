# AM-203 · ClaudeCliAdapter + fałszywy `claude` do testów

Issue: #19 · Wymagania: FR-S3, FR-S4, FR-S2 (lista), NFR-3, ENG-C8, ENG-I4, ENG-T2, ENG-T3 · docs/11 §4, §6, §7, docs/12 (fałszywy `claude`), ADR 0002 · Etap: M2

## Zakres

`ClaudeCliAdapter` (`internal`) implementuje `AgentRuntime` przez `ProcessRunner` z `core:process` i parser z AM-202. Publiczna jest tylko fabryka `agentRuntimeModule()`. Fałszywy `claude` (skrypt POSIX `sh` ze stanem w plikach) służy testom integracyjnym i kontraktowym, więc adapter przechodzi `AgentRuntimeContract` na `RuntimeWorld`.

Nie robimy: `health()` (AM-204), hooków (AM-601/602), wpięcia w `app` (`CoreDeps` nie ma jeszcze `ProcessRunner`; adapter wpina pierwszy konsument, `sessions:impl`), PTY dla `attach` (`terminal`), `--exec`, `--resume`.

**Flagi CLI.** W tej sesji nie dało się uruchomić `claude … --help` (subagent architekta nie ma narzędzia powłoki). Flagi wziąłem z oficjalnej dokumentacji Agent View (code.claude.com/docs/en/agent-view, changelog do 2.1.290). Implementer sprawdza `claude --help`, `claude agents|attach|logs|stop|respawn|rm --help` przed pierwszym commitem i zapisuje różnice w PR (pytanie 3). Najważniejsze fakty z dokumentacji:

- `claude --bg [--name N] [--agent A] [--model M] [--permission-mode P] "<prompt>"` wypisuje `backgrounded · 7c5dcf5d · <name>`, czasem po linii `Starting background service…`. `--bg` z `-p` jest odrzucane. Od 2.1.281 nieufny katalog daje błąd `Workspace not trusted`.
- `claude agents --json [--all]`: `--all` dodaje zakończone sesje. `--cwd` jest od **2.1.141** (minimum to 2.1.139), a jego semantyka („started under that directory”, także worktree w `.claude/worktrees/`) nie jest jednoznaczna.
- `claude logs <id>`: bez flag (brak `--lines`), długość wyjścia nieopisana. `claude stop <id>`, `claude respawn <id>` (działa też na sesji `WORKING`), `claude attach <id>`.
- `claude rm <id>` usuwa wiersz i może usunąć worktree utworzony przez Claude (nigdy z niezapisanymi zmianami lub niewypchniętymi commitami). Gdy odmawia, wypisuje `kept <id>` z powodem. Kody wyjścia i komunikat dla nieznanego id nie są opisane.

## Moduły

- `feature:agent-runtime:impl`: adapter, fabryka, czyste funkcje pomocnicze, fałszywy `claude`, testy. `build.gradle.kts`: `implementation(project(":core:process"))`, `testImplementation(testFixtures(project(":core:process")))` (`FakeProcessRunner`), `testImplementation(project(":core:testing"))`. Reguła `impl → core:*` na to pozwala, nowych bibliotek nie ma, więc ADR nie jest potrzebny.
- `feature:agent-runtime:api`, **tylko `src/testFixtures`**: jedna właściwość w `AgentRuntimeContract` (pytanie 1). `src/main` się nie zmienia.
- `core:process` (zmiana spoza pierwotnej roadmapy, osobny commit `fix(process)`): `LoginShellProcessRunner` nie czeka do EOF na potoki trzymane przez dziecko w tle: wynik to wyjście do wyjścia procesu plus najwyżej 1 s. Bez tego `start` (`claude --bg`) mógł wisieć bez timeoutu. Dzieci w tle nie są zabijane, ale po wyjściu procesu JDK zamyka potoki, więc ich dalsze zapisy na odziedziczony stdout/stderr mogą dostać EPIPE/SIGPIPE; proces, który ma przeżyć wywołanie, musi odłączyć stdio (ryzyko znane, pytanie 3). API `ProcessRunner` bez zmian.
- `docs/compat.md`: `--cwd` od 2.1.141 i nieużywane, wiersz `--bg` (format `backgrounded ·`), `rm` (`kept`, worktree).

## Zmiany API

`agent-runtime:api` `src/main`: brak. testFixtures (pytanie 1):

```kotlin
public abstract class AgentRuntimeContract {
    /** Existing directory used as `cwd` by every `start` in this contract; the CLI adapter runs `claude --bg` in it. */
    protected open val startCwd: Path = A_PROJECT_DIR   // all aStartSpec(...) calls get cwd = startCwd
}
```

Publiczna fabryka (jedyna deklaracja publiczna w `impl`, reguła Konsist `impl exposes only its module factory`; dlatego bez publicznego `RuntimeConfig`):

```kotlin
/**
 * Creates the Claude Code CLI adapter of [AgentRuntime] (ADR 0002). Thread-safe and stateless.
 * @param executable `claude` on the login-shell PATH, or an absolute path (tests).
 * @param homeDir working directory of every command except `start`, and of [AgentRuntime.attachCommand].
 * @param commandTimeout limit of `agents`, `logs`, `stop`, `respawn`, `rm`; [startTimeout] limits `--bg` (docs/11 §6).
 */
public fun agentRuntimeModule(
    process: ProcessRunner, clock: Clock, logger: Logger, homeDir: Path,
    executable: String = "claude", commandTimeout: Duration = 10.seconds, startTimeout: Duration = 30.seconds,
): AgentRuntime
```

Wewnętrzne (`internal`, KDoc po angielsku):

```kotlin
internal class ClaudeCliAdapter(/* the factory parameters */) : AgentRuntime
internal object ClaudeCommands {           // pure argv builders
    fun list(): List<String>               // [exe, "agents", "--json", "--all"]
    fun start(spec: StartSpec): List<String> // [exe, "--bg", "--name", n?, "--agent", a?, "--model", m?, "--permission-mode", p?, "--", prompt]
    fun byId(verb: String, id: SessionId): List<String>  // verb ∈ attach, logs, stop, respawn, rm
}
internal object BgOutput { fun sessionId(stdout: String): SessionId? }  // first `backgrounded · <id>` line
internal object OutputTail { const val MAX_LINES = 200; const val MAX_CHARS = 16_384; fun of(stdout: String): String }
internal object StderrTail { const val MAX_CHARS = 512; fun of(stderr: String, secrets: List<String>): String }
internal fun RuntimeSession.isUnder(dir: Path): Boolean   // normalize() + startsWith (Path components)
```

### Zachowanie adaptera

- `listSessions(under)`: `agents --json --all` (bez `--cwd`, bo minimum 2.1.139 go nie ma), parser AM-202 z `observedAt = clock.now()`, filtr `isUnder` po stronie klienta. `notices` idą do loggera na poziomie DEBUG (tylko kategorie i liczby).
- `start`: `ShellCommand(argv, workDir = spec.cwd)`, `startTimeout`. Prompt jest po `--`, żeby tekst zaczynający się od `-` nie był czytany jako flaga. Id bierzemy z `BgOutput`, a jego brak przy kodzie 0 daje `Unparseable("bg-output:no-id")`.
- `stop`, `respawn`, `remove`, `recentOutput`: polecenie z `byId`. Przy kodzie ≠ 0 adapter jeszcze raz robi `list()`: jeśli id nie ma na liście, zwraca `UnknownSession(id)`, w przeciwnym razie `CommandFailed`. `rm` z kodem 0, ale z linią `kept <id>`, daje `CommandFailed(exitCode, tail)`. `recentOutput` zwraca `OutputTail.of(stdout)`: bez sekwencji ANSI i znaków sterujących (poza `\n`, `\t`), z `trimEnd()`, ostatnie 200 linii i 16 KiB.
- `attachCommand(id)`: `ShellCommand([exe, "attach", id], workDir = homeDir)`, bez IO.
- `health()` do czasu AM-204 zwraca `RuntimeHealth(version = null, agentViewEnabled = false, supervisorRunning = false, problems = [Unparseable("health:not-checked")])`. `isReady = false`, więc nic nie udaje gotowości. `AgentRuntimeHealthContract` nie jest uruchamiany na adapterze; `ClaudeCliAdapterHealthContractTest` dodaje AM-204.

Błędy procesu:

| `ProcessError` / wynik | `RuntimeError` |
| --- | --- |
| `NotFound` | `NotInstalled` |
| `Timeout` | `Timeout` |
| `StartFailed`, `IoFailed` | `CommandFailed(-1, "process:start-failed" / "process:io-failed")`; `reason` się nie przenosi (może zawierać ścieżki) |
| kod ≠ 0 | `UnknownSession` albo `CommandFailed(code, StderrTail.of(stderr, secrets = [spec.prompt]))` |
| `agents`: kod 0, parser `Err` | ten sam `Unparseable` (puste stdout to `EMPTY`, zgodnie z AM-202 pyt. 4) |

`StderrTail.of`: usuwa ANSI i znaki sterujące, zamienia każde wystąpienie `secrets` na `***`, `/Users/<x>/` i `/home/<x>/` na `~/`, `sk-ant-[A-Za-z0-9_-]+` i `Bearer \S+` na `***`, a potem bierze ostatnie 5 linii i ≤ 512 znaków. Prompt nie trafia do logów (logger dostaje tylko czasownik i id).

## Fałszywy `claude`

`src/test/resources/fake-claude/fake-claude.sh` (POSIX `sh`, bez `jq` i Pythona) i `src/test/kotlin/…/FakeClaude.kt`. `FakeClaude.install(dir, world, now)` tworzy `bin/claude`: wrapper `exec /bin/sh <dir>/fake-claude.sh <dir>/state "$@"` z prawami `+x`. Test podaje adapterowi `executable = <dir>/bin/claude` (ścieżka absolutna), żeby prawdziwy `claude` z `PATH` lub z `path_helper` na macOS nigdy nie został wywołany. Przy `installed = false` `executable` to nazwa, której nie ma na `PATH` (`claude-am-missing-<uuid>`), co daje `NotFound`.

Stan w `state/`: `sessions.tsv` (jedna sesja w linii: `id`, `sessionId`, `name`, `cwd`, `state`, `waitingFor`, `startedAt` w ms, `pid`), `logs/<id>`, `counter`, `now` (stały czas zamiast zegara), `calls.log` (argv każdego wywołania, do asercji flag), `mode` (`normal` | `garbage` | `hang` | `fail <kod> <stderr>` | `bg-child`). Mapowanie świata: faza → `working|blocked|done|failed|stopped`, `Permission` → `permission prompt`, `Input` → `input needed`, `Other(raw)` → `raw`.

| Wywołanie | Zachowanie fałszywki |
| --- | --- |
| `agents --json [--all]` | tablica JSON w formacie `synthetic/background-all-phases.json` (`kind: "background"`); bez `--all` ukrywa `done`, `failed` i `stopped` |
| `--bg … -- <prompt>` | `id = printf %08x` z licznika, `cwd = $(pwd)`, `state = working`; wypisuje `backgrounded · <id> · <name>` |
| `stop` / `respawn` / `rm` `<id>` | `stopped` (pid pusty) / `working` / usunięcie linii |
| `logs <id>` | `cat logs/<id>`, a gdy pliku nie ma, nic |
| nieznane `<id>` | stderr `fake-claude: no session <id>`, kod 1 |

`cwd` startu: test tworzy `startCwd` przez `toRealPath()`, bo na macOS `/var/folders` to dowiązanie do `/private/var`, a `pwd` w skrypcie zwraca ścieżkę fizyczną.

## Ryzyka i pytania

- **Świadomy wyjątek od ENG-C6 w `core:process`.** Blokującego `read()` z potoku nie da się anulować, a `close()` go nie odblokowuje (sprawdzone na JDK 21/Linux). Dlatego czytelnicy potoków żyją na własnych wątkach demona (jeden wątek i bufor 8 KiB na potok, bez trzymania wyjścia), dopóki JDK albo potomek nie zwolni potoku; nie zajmują w tym czasie `Dispatchers.IO`. Do akceptacji przez człowieka w PR.
- **EPIPE dla potomków, które nie odłączają stdio (ryzyko znane).** Przy `Redirect.PIPE` sam JDK zamyka deskryptory potoków po wyjściu bezpośredniego dziecka (reaper → `ProcessPipeInputStream.processExited()`), niezależnie od naszego czytelnika. Wnuk w tle, który dalej pisze na odziedziczony stdout/stderr, dostaje wtedy EPIPE/SIGPIPE. Przyjmujemy to świadomie: główny cel (wywołanie nie wisi na potomku w tle) jest spełniony, a dobrze zachowujący się demon (supervisor `claude --bg`) odłącza stdio. Sprawdzenie na macOS, że usługa przeżywa `start`, jest częścią pytania 3.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Zmiana testFixtures w `agent-runtime:api`** (spoza listy modułów w roadmapie, ale w tym samym feature, bez zmian w `src/main`). Kontrakt startuje w `/Users/test/projects/…`, a prawdziwy runner potrzebuje istniejącego katalogu roboczego. Bez tej zmiany `start` kończy się `StartFailed`. Rekomendacja: dodać `protected open val startCwd` i zaktualizować wiersz roadmapy (moduły: `agent-runtime:impl`, `agent-runtime:api` testFixtures).
2. **`remove` a „never deletes project files”.** `claude rm` może usunąć worktree utworzony przez Claude (`.claude/worktrees/…`, tylko czysty i wypchnięty). Rekomendacja: doprecyzować KDoc `remove` (bez zmiany sygnatury) w tym PR albo w osobnym `docs/`. Brak `RuntimeError.RemoveRefused` (dla `kept`) jest świadomy: na razie `CommandFailed`.
3. **Brak `--help` i nagrania sesji w tle.** Flagi z dokumentacji potwierdzono w `claude --help` 2.1.302 (`attach`/`logs` `<id|name>`, `stop`/`rm` `<id>`, `respawn <id>|--all`, `--permission-mode` bez wartości `default`), ale format `agents --json` sesji w tle pochodzi z fixtures syntetycznych AM-202. Fałszywy `claude` emituje dokładnie ten format, więc zielony kontrakt dowodzi zgodności z naszym założeniem, a nie z CLI. Rekomendacja: przed scaleniem człowiek na macOS uruchamia `claude --bg`, `agents --json --all` w fazach working/blocked/done/stopped, `logs`, `stop`, `respawn`, `rm` i nieznane id (kod wyjścia, stderr). Nagrania trafiają do `fixtures/…/recorded/`, a fałszywka i mapowanie są poprawiane w tym samym PR. Przy okazji sprawdza, że usługa po `claude --bg` żyje po powrocie `start` z aplikacji (brak EPIPE/SIGPIPE, zob. ryzyko EPIPE wyżej).
4. **Fabryka zwraca `AgentRuntime`**, a nie obiekt z docs/11 §9 (`runtime.agentRuntime`, `runtime.hookInstaller`). Publiczny typ-pojemnik nie może leżeć w `impl` (Konsist), a tworzenie go teraz w `api` wyprzedza AM-601/602. Rekomendacja: AM-601 dodaje pojemnik w `agent-runtime:api` i zmienia typ zwracany (dotyka tylko `app`).
5. **`health()` zwraca „not ready” z `Unparseable("health:not-checked")`** do AM-204, zamiast udawać gotowość. Alternatywa: `RuntimeError.Unknown`, ale to zmiana `api`. Rekomendacja: zostawić; `app` i tak nie woła jeszcze adaptera.

Decyzje z implementacji:

- `PermissionMode.DEFAULT` nie przekazuje `--permission-mode`: claude 2.1.302 nie zna wartości `default` (dozwolone: `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk`, `plan`), więc tryb domyślny to brak flagi. Wiersz `DEFAULT` w `ClaudeCommandsTest` zastąpił osobny test `default permission mode passes no flag`.
- `ClaudeCommands` przyjmuje `executable` jako pierwszy argument (`list(exe)`, `start(exe, spec)`, `byId(exe, verb, id)`).
- `rm`: linię `kept <id>` adapter szuka w stdout i w stderr; ogon w `CommandFailed` powstaje z obu strumieni.
- detekt `LongParameterList`: konstruktor adaptera przyjmuje `internal data class CliConfig(homeDir, executable, commandTimeout, startTimeout)`; publiczna fabryka ma `@Suppress` z uzasadnieniem w KDoc (w `impl` nie może być publicznego typu ustawień).
- `core:process` (osobna zmiana): `LoginShellProcessRunner` po wyjściu procesu czeka na koniec obu potoków najwyżej 1 s (wspólny termin) i zwraca to, co przeczytał. Czytelnik każdego potoku działa na własnym wątku demona `am-pipe-drain-<n>`, bo blokującego `read()` nie da się anulować, a nie chcemy zajmować `Dispatchers.IO`, dopóki JDK albo potomek nie zwolni potoku; kończy się sam przy EOF lub błędzie odczytu (dowolny wyjątek kończy oczekiwanie). Dzieci w tle nie są zabijane, ale **nie są chronione przed EPIPE**: po wyjściu procesu JDK zamyka potoki, więc procesy, które mają przeżyć wywołanie, muszą odłączyć stdio. Przy anulowaniu lub timeoucie drzewo procesów dostaje SIGKILL, a czekanie na jego zebranie jest ograniczone (1 s). API `ProcessRunner` bez zmian.

Ryzyka:

- Nieznane id rozpoznajemy po ponownej liście, a nie po treści stderr. Jeśli prawdziwe CLI zwraca kod 0 dla nieznanego id, adapter zgłosi `Ok`. Wtedy zmieniamy to na sprawdzenie listy przed poleceniem (mała zmiana, testy już są).
- `ProcessRunner` trzyma **początek** wyjścia (1 MiB), a `recentOutput` potrzebuje końca. Przy `logs` większym niż 1 MiB ogon jest zły. Adapter ustawia `maxOutputBytes = 4 MiB`, a gdy `stdoutTruncated`, zapisuje WARN. Pełne rozwiązanie wymaga zmiany `core:process` i jest poza zakresem.
- `claude agents` w nieufnym katalogu (2.1.225) i `respawn` (2.1.281) sprawdzają zaufanie do katalogu. Uruchamiamy je w `homeDir`. Jeśli `--json` też pokazuje dialog, polecenie może wisieć do timeoutu (`Timeout`). Do weryfikacji w pytaniu 3.
- `--` przed promptem zakłada parser opcji, który go honoruje (commander.js tak robi). Jeśli nie, prompt zawiera `--` dosłownie. Weryfikacja w pytaniu 3.
- Testy przez `/bin/sh -l` czytają `/etc/profile`. `executable` jako ścieżka absolutna uodparnia je na `PATH`, a `HOME` procesu dziecka pozostaje prawdziwy (adapter nie ustawia `env`).
- PR: kod produkcyjny ok. 300 linii, poniżej limitu ENG-C10. Skrypt i testy nie liczą się do limitu.
