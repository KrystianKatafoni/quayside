# AM-302 · JsonProjectStore

Issue: #22 · Wymagania: FR-P1, FR-P3, ENG-C6, ENG-C8, ENG-I4, ENG-I5, ENG-T2, ENG-T3 · docs/11 §6, §8, ADR 0009 (proponowana) · Etap: M3

## Zakres

Nowy moduł `feature:projects:impl` (skill `/new-module projects impl`): `JsonProjectStore` (`internal`) implementuje `ProjectsApi` na `JsonStore` z `core:storage` i przechodzi `ProjectsApiContract`. Publiczna jest tylko fabryka `projectsModule(...)`.

Nie robimy: `DirectoryInspector` (AM-303), UI (AM-304), wpięcia w `app` (`CoreDeps` nie ma jeszcze `JsonStorage`; pytanie 2), zmian `projects:api` (KDoc z AM-301 jest specyfikacją), ponownego sprawdzania katalogów przy starcie.

## Moduły

- `feature:projects:impl` (nowy), `settings.gradle.kts` (`include(":feature:projects:impl")`). `docs/adr/0009-format-projects-json.md` (szkic).
- `build.gradle.kts`: `am.feature.impl`; `implementation` `:feature:projects:api`, `:core:domain`, `:core:storage` (daje `kotlinx-serialization-json` jako `api`); `testImplementation` `testFixtures(:feature:projects:api)`, `testFixtures(:core:storage)` (`InMemoryJsonStore`), `:core:testing` (`RecordingLogger`). Reguła `impl → core:*` na to pozwala; bez nowych bibliotek i bez pluginu kompilatora serializacji.
- Pakiet `dev.agentmanager.projects.impl`. Hierarchie `sealed` w `impl` jako `sealed class` (Konsist); plan żadnej nie wymaga.

## Zmiany API

`projects:api`: brak. Publiczna fabryka (jedyna deklaracja publiczna w `impl`):

```kotlin
/**
 * Opens the project list stored as `projects.json` in [storage] and returns it as [ProjectsApi].
 * Suspends until the file is loaded, so [ProjectsApi.storageIssue] and [ProjectsApi.projects] are final
 * on return; never throws except cancellation. The caller picks the directory (`JsonStorage(appSupportDir, …)`).
 * @param io dispatcher for path resolution (`toRealPath()`), usually `AppDispatchers.io`.
 * @param logger gets project ids and fixed categories only, never paths or display names (ENG-C8).
 */
public suspend fun projectsModule(storage: JsonStorage, io: CoroutineDispatcher, logger: Logger): ProjectsApi
```

Wewnętrzne (KDoc po angielsku):

```kotlin
internal class JsonProjectStore private constructor(
    private val store: JsonStore<List<Project>>, private val io: CoroutineDispatcher, private val logger: Logger,
    private val newId: () -> ProjectId, initial: List<Project>, issue: StorageIssue?,
) : ProjectsApi {
    companion object {
        const val FILE_NAME = "projects.json"
        /** Loads once and maps the result with [StartupState.of]. */
        suspend fun open(store: JsonStore<List<Project>>, io: CoroutineDispatcher, logger: Logger,
                         newId: () -> ProjectId = { ProjectId(UUID.randomUUID().toString()) }): JsonProjectStore
    }
}
internal data class StartupState(val projects: List<Project>, val issue: StorageIssue?, val blockedBy: StorageProblem?) {
    companion object { fun of(loaded: Outcome<Loaded<List<Project>>, StorageError>): StartupState }   // pure
}
internal fun StorageError.toWriteProblem(): StorageProblem          // pure, always WRITE_FAILED (see table)
internal object ProjectListSerializer : KSerializer<List<Project>>  // JsonElement surrogate, ADR 0009
internal object RealPaths { suspend fun resolve(dir: Path, io: CoroutineDispatcher): Outcome<Path, ProjectError> }
```

### Decyzje

1. **Format** (ADR 0009): koperta `JsonStore`, `data = {"projects": [{id, dir, displayName}]}`, `schemaVersion = 1`, `StoreSpec(FILE_NAME, ProjectListSerializer, emptyList())`. `data` jako obiekt, bo `Migration` z AM-107 działa na `JsonObject`. Serializer ręczny (`JsonDecoder.decodeJsonElement()`), bo w repo nie ma pluginu kompilatora; dekodowanie rzuca `SerializationException` przy brakującym polu, pustym `id`, ścieżce względnej lub nieparsowalnej, powtórzonym `id` albo `dir`, więc `JsonStore` odkłada plik jako `.broken`. `dir` z pliku nie jest ponownie rozwiązywany (katalog może być na odmontowanym dysku); `displayName` nie jest walidowany ponownie (zmiana reguł nie psuje starych plików), tylko niepusty.
2. **Miejsce pliku**: parametr `storage: JsonStorage`; `impl` zna tylko nazwę `projects.json` (docs/11 §8, jeden właściciel). Ścieżkę katalogu wybiera `app`.
3. **`ProjectId`**: losowy `java.util.UUID` (napis), wstrzykiwany jako `newId` (testy: licznik `p1, p2, …`). Bez zegara: znaczniki czasu kolidują przy współbieżnym `add` i niosą znaczenie, którego id ma nie mieć. Bez licznika: licznik trzeba by utrwalać w pliku, a po usunięciu ostatniego projektu id wróciłoby do obiegu (cudze ustawienia per projekt wskazałyby nowy projekt). Gdy `newId` zwróci id już obecne na liście, losujemy ponownie (obrona przed złym źródłem w testach). `kotlin.uuid.Uuid` odpada (eksperymentalne, `allWarningsAsErrors`).
4. **Start**: fabryka `suspend` woła `store.load()` raz i tworzy `MutableStateFlow`y od razu z wartościami końcowymi, więc `storageIssue` jest ustalone, zanim `projects` pokaże listę, i nigdy się nie zmienia. Brak zakresu w tle i `launch` (ENG-C6 bez wstrzykiwanego `CoroutineScope`), komendy nie czekają na `Deferred`, a UI nie miga pustą listą. Kontrakt (`create` nie jest `suspend`) woła fabrykę przez `runBlocking` (dozwolone w testach).
5. **Komendy**: kolejność kontroli jak w `FakeProjectsApi`: `blockedBy` → `StorageFailed`; walidacja `ProjectInputRules`; `RealPaths.resolve` na `io` poza blokadą (`toRealPath()`, każdy `IOException`/`SecurityException` → `NotFound(znormalizowana)`, nie katalog → `NotADirectory`). Potem pod własnym `Mutex` (osobnym od `Mutex` w `JsonStore`): kontrola duplikatu po ścieżce rzeczywistej / istnienia id, nowa lista, `store.save(lista)`, dopiero po `Ok` `state.value = lista`. `save` zamiast `update`, bo pamięć jest źródłem prawdy, a `update` czytałby plik ponownie. `save` i ustawienie stanu w `withContext(NonCancellable)`: anulowanie po atomowym `move` nie może zostawić pliku i `projects` w różnych stanach.
6. **Mapowanie błędów**:

   | Wejście | `storageIssue` | Komendy |
   | --- | --- | --- |
   | `load` `Ok(Loaded(v, recovered = null))` | `null` | działają, lista `v` |
   | `load` `Ok(Loaded(_, recovered ≠ null))` | `RECOVERED_FROM_BROKEN_FILE` | działają, lista pusta |
   | `load` `Err(NewerSchema)` | `NEWER_SCHEMA` | `StorageFailed(NEWER_SCHEMA)`, plik nietknięty |
   | `load` `Err(IoFailed)` (odczyt, przeniesienie `.broken`, zapis po migracji) | `READ_FAILED` | `StorageFailed(READ_FAILED)`, plik nietknięty |
   | `save` `Err(IoFailed)` / `Err(NewerSchema)` | bez zmian | ta komenda `StorageFailed(WRITE_FAILED)`, lista bez zmian |

7. **Logowanie** (ENG-C8): INFO `project added|removed|renamed` z `projectId`; WARN `projects file recovered from a broken copy` / `projects file unreadable|newer schema` / `projects file save failed` tylko z kategorią. `StorageError.IoFailed.path` i `.reason` (komunikat wyjątku może cytować ścieżkę) oraz `BrokenFile.movedTo` nigdy nie trafiają do logów ani błędów.

## Ryzyka i pytania

Pytania blokujące: brak. Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Fabryka `suspend`.** `app` wywoła ją przed pokazaniem okna (`runBlocking` w `main` albo w zakresie aplikacji ze stanem „ładowanie”). Alternatywa: fabryka zwykła z ładowaniem w tle we wstrzykniętym `CoroutineScope`; komendy czekają wtedy na `Deferred`, a UI widzi pustą listę przed wczytaniem (KDoc `projects` nie odróżnia „jeszcze nie wczytano”). Rekomendacja: `suspend`, odczyt kilku KB.
2. **Kto wpina moduł w `app`.** Roadmapa nie ma tego wpisu; AM-304 ma tylko `projects:ui`. Rekomendacja: dopisać `app` do AM-304 (dodanie `storage: JsonStorage` do `CoreDeps` i wywołanie fabryki).
3. **ADR 0009 (format, UUID, ręczny serializer, cały plik `.broken` przy błędnym wpisie)** do przyjęcia. Alternatywa dla ostatniego punktu: pomijać błędne wpisy, ale bez komunikatu w UI to ciche gubienie danych.
4. **AM-303 doda drugą fabrykę** (`projectInspectorModule(...)`) zamiast zmieniać typ zwracany `projectsModule`; Konsist sprawdza tylko klasy, interfejsy i obiekty, więc funkcje publiczne są dozwolone.

Ryzyka:

- `IoFailed` z `JsonStore` nie mówi, czy zawiódł odczyt, przeniesienie do `.broken`, czy zapis po migracji; przy `load` wszystkie traktujemy jako `READ_FAILED` (plik i tak nie jest nadpisywany). Rozróżnienie wymagałoby zmiany `core:storage`.
- Dwa `JsonStorage` na tym samym katalogu (np. dwie instancje aplikacji) nie są serializowane; ostatni zapis wygrywa. Poza zakresem (jedna instancja aplikacji na macOS).
- `Path.of` przy kodowaniu ścieżek innym niż UTF-8 (`sun.jnu.encoding`) rzuca dla nazw spoza ASCII; w serializerze to wyjątek → `.broken`. Test z emoji w nazwie katalogu tylko w kontrakcie (prawdziwe katalogi), nie w serializerze.
- Testy z prawami dostępu nie działają jako root; deterministyczny wariant (katalog zamiast pliku) jest główny, `chmod` z `assume`.
- PR: kod produkcyjny ok. 250 linii, poniżej limitu ENG-C10.
