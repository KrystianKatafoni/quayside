# AM-304 · projects:ui: sidebar, dodaj z dysku, usuń z dialogiem

Issue: #24 · Wymagania: FR-P1, FR-P2 (prezentacja), FR-P3, FR-P4, NFR-10, ENG-C6, ENG-C8, ENG-C10, ENG-T4 · docs/11 §1 (MVI), §3, §9 · Etap: M3

## Zakres

Nowy moduł `feature:projects:ui` (skill `/new-module projects`, tylko część `ui`) oraz minimalne podpięcie `projects` w `app`.

- **Część A** (FR-P1, FR-P2, FR-P3, FR-P4): sidebar z listą projektów i zaznaczeniem, stan pusty z przyciskiem „Dodaj projekt”, baner `StorageIssue`. Dodawanie: wybór folderu (`DirectoryPicker`), potem stan „Sprawdzanie…”, potem dialog z raportem `ProjectInspector` i przyciskiem „Dodaj”. Usuwanie (menu ⋯, ⌘⌫) z dialogiem potwierdzenia. Gdy w projekcie działają sesje, dialog ma trzy przyciski: „Zatrzymaj sesje i usuń”, „Usuń z listy, sesje działają dalej”, „Anuluj”.
- **Część B** (FR-P6: zmiana nazwy, liczniki „pracuje/czeka”) przechodzi do **AM-305** (decyzja z pytania 1). Typ `SessionCounts` i parametr `sessionCounts` kontrolera dochodzą dopiero tam.
- **`app`**: `CoreDeps` dostaje `process` i `storage`. Composition root tworzy `agentRuntimeModule`, `projectsModule` (`runBlocking` w `main`, dozwolone), `projectInspectorModule` i `ProjectsController`. Okno ma układ `Row(sidebar, Mission Control)`, a `MenuBar` ma pozycje „Dodaj projekt…” (⌘⇧O) i „Usuń projekt” (⌘⌫). `AwtDirectoryPicker` używa `java.awt.FileDialog` z `apple.awt.fileDialogForDirectories=true`, które na macOS otwiera natywny `NSOpenPanel`.

Nie robimy: komend palety (AM-406), wyboru nazwy przy dodawaniu (zmiana nazwy po dodaniu), `core:design-system`/`AmTheme` (AM-802; kolory jako stałe `internal`), modułu `tests:functional` (AM-904), zmian `projects:api`, `agent-runtime:api` ani `core:process`.

## Zmiany API

`projects:api`, `agent-runtime:api`: brak. Publiczne typy `projects:ui` (KDoc po angielsku):

```kotlin
/** Opens the system folder chooser. Must be called on the UI thread; null = the user cancelled. */
public fun interface DirectoryPicker { public suspend fun pick(): Path? }

/** Which window-menu commands are enabled; both false while a dialog is open, so ⌘⌫ reaches text fields. */
public data class ProjectsMenuState(val canAdd: Boolean, val canRemove: Boolean)

/** User intents from the sidebar and the window menu (MVI, docs/11 §1). */
public sealed interface ProjectsIntent {
    public data object AddRequested : ProjectsIntent             // ⌘⇧O, sidebar button
    public data object RemoveSelectedRequested : ProjectsIntent  // ⌘⌫; ignored without a selection
}

/**
 * State holder of the projects sidebar. Runs every command in [scope] (the window scope, Main dispatcher);
 * at most one dialog flow at a time, further requests are ignored until it ends. Never throws: errors
 * become fixed texts without paths (ENG-C8). Logs only fixed categories and project ids.
 */
public class ProjectsController(
    projects: ProjectsApi, inspector: ProjectInspector, runtime: AgentRuntime, picker: DirectoryPicker,
    scope: CoroutineScope, logger: Logger,
) {
    public val menu: StateFlow<ProjectsMenuState>
    public fun onIntent(intent: ProjectsIntent)
    internal val state: StateFlow<ProjectsUiState>               // read by the composables only
    internal fun onEvent(event: SidebarEvent)                     // clicks inside the sidebar and dialogs
}

/** The sidebar with its dialogs; stateless apart from [controller]. */
@Composable public fun ProjectsSidebar(controller: ProjectsController, modifier: Modifier = Modifier)
```

Sześć parametrów konstruktora (detekt dopuszcza 6). Wewnętrzne: `ProjectsUiState(projects, selected, banner, dialog)`; `sealed interface Dialog { Picking; enum Waiting(INSPECTING, CHECKING_SESSIONS, BUSY); ConfirmAdd(report, error); ConfirmRemove(project, sessions: List<SessionId>?); Message(text) }`; `sealed interface SidebarEvent` (Select, ConfirmAdd, StopAndRemove, RemoveKeepSessions, Dismiss, DismissBanner). `menu` wynika ze stanu (`dialog == null`); każde potwierdzenie ustawia stan oczekiwania synchronicznie przed `launch`, więc drugie kliknięcie jest ignorowane (poprawka po review).

Czyste funkcje (`internal object`):

### Decyzje

1. **FR-P4 bez `sessions`.** Po otwarciu dialogu kontroler woła `runtime.listSessions(under = project.dir)`, a `ActiveSessions` wybiera `WORKING` i `BLOCKED` (ta sama semantyka co inspektor, AM-303 pyt. 2). Liczba 0 daje zwykły dialog potwierdzenia. `Err` daje dialog z tekstem „Nie udało się sprawdzić sesji” i tylko opcją „Usuń z listy”. „Zatrzymaj i usuń” woła `stop` po kolei. Jeśli któreś `stop` się nie uda, projekt **zostaje** na liście i pojawia się komunikat. Logika DRY z `impl` jest świadomie zduplikowana: `ui` nie widzi `impl`, ENG-C9. AM-404 podmieni to na `SessionCommands.stopAllIn`.
2. **Dodawanie.** `picker.pick()` → `inspect`. `Err` → `Message(ProjectMessages.of(e))`. `alreadyAdded != null` → zaznaczenie istniejącego projektu i komunikat „już na liście”, bez `add`. W pozostałych przypadkach `ConfirmAdd(report)` → `projects.add(report.dir)`. `Ok` → zaznaczenie nowego projektu. `Err` → komunikat w dialogu.
3. **Komunikaty.** Każdy wariant `ProjectError` (z `NameProblem`, `StorageProblem`) i `StorageIssue` ma stały klucz. Żaden tekst nie zawiera ścieżki. W raporcie dodawania UI pokazuje `report.dir` i gałąź, bo KDoc `ProjectError` dopuszcza ścieżki w UI. `TOO_LONG` dostaje argument `MAX_DISPLAY_NAME_LENGTH`.
4. **Dialogi w oknie, nie osobne okna.** Nakładka `Box` z przyciemnieniem, a menu ⋯ jako `Popup`. `runComposeUiTest` obsługuje je w jednej scenie. Biblioteki Material nie ma (tylko `foundation`), więc przyciski i pole tekstowe budujemy z `BasicText` i `BasicTextField`.
5. **Logi a ścieżki (ryzyko z AM-303).** `LoginShellProcessRunner` loguje `workDir` tylko na DEBUG. KDoc `Project` i `ProjectError` dopuszczają ścieżki na DEBUG, więc `core:process` nie wymaga zmiany. Najmniejszy krok: `simplelogger.properties` w `app` z jawnym `org.slf4j.simpleLogger.defaultLogLevel=info` oraz test, który pilnuje, że produkcyjny logger ma DEBUG wyłączony.
6. **`AwtDirectoryPicker`** (`internal`, `app`) nie ma w nazwie sufiksu `Adapter`, bo Konsist dopuszcza `*Adapter` tylko w `impl`. Woła `FileDialog` przez `withContext(Dispatchers.Main)`; modalny dialog AWT obsługuje zdarzenia EDT. Właściwość `apple.awt.fileDialogForDirectories` ustawiamy w `main` przed pierwszym użyciem AWT. Katalog `projects.json` to `~/Library/Application Support/AgentManager`, `homeDir` runtime to `user.home`.

## Ryzyka i pytania

Pytania blokujące (rozstrzygnięte):

1. **ENG-C10 (≤ 400 linii kodu produkcyjnego na PR).** Rozstrzygnięte: część B (FR-P6) przechodzi do nowego zadania **AM-305** (zależy od AM-304, dane liczników po AM-403). AM-304 to ok. 410 linii; nadwyżkę opisuje PR.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **FR-P4 przez `AgentRuntime`, nie `SessionCommands`.** `sessions:api` jeszcze nie istnieje. Rekomendacja: `projects:ui` → `agent-runtime:api` teraz; AM-404/405 podmienia na `stopAllIn`.
2. **Częściowe niepowodzenie „zatrzymaj i usuń”.** Rekomendacja: projekt zostaje na liście (część sesji mogła się zatrzymać), komunikat podpowiada drugą opcję. Alternatywa: usuwać mimo błędu.

Ryzyka:

- `FileDialog` z `fileDialogForDirectories` to zachowanie JDK specyficzne dla macOS; na Linuksie (CI) pokazuje wybór plików, ale CI go nie uruchamia. Fallback `JFileChooser` z `DIRECTORIES_ONLY` dopiero przy problemie.
- ⌘⌫ w `MenuBar` mógłby przechwycić skrót w polu tekstowym. Dlatego `menu.canRemove = false` przy otwartym dialogu; sprawdzenie ręczne na Macu.
- `runBlocking { projectsModule(...) }` w `main` opóźnia otwarcie okna o odczyt małego pliku JSON. Wolny dysk sieciowy jest mało prawdopodobny dla Application Support.
- Inspekcja trwa do ok. 10 s (AM-303). Stan „Sprawdzanie…” ma przycisk „Anuluj”, który anuluje zadanie.
- Duplikat reguły „aktywna sesja” w `ui` i `impl` może się rozjechać. Pilnują go testy tablicowe po obu stronach, docelowo zniknie w AM-404.
