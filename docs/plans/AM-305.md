# AM-305 · projects:ui: zmiana nazwy, liczniki sesji w sidebarze i usuwanie przez `stopAllIn`

Issue: #74 · Wymagania: FR-P6, FR-P4 (pod NFR-10, ENG-I2, ENG-C6, ENG-C8, ENG-C9, ENG-C10, ENG-T4) · docs/11 §1 (MVI), §3, §6, §9 · Etap: M3/M4 · Zależy: AM-304, AM-404, **po scaleniu AM-405** (koordynacja niżej)

## Zakres

Część B z AM-304 oraz podmiana obejścia FR-P4 na `sessions`:

1. **Zmiana nazwy (FR-P6).** Menu ⋯ wiersza dostaje „Zmień nazwę…”. Otwiera dialog z polem tekstowym (`BasicTextField`) z bieżącą nazwą. Enter albo „Zapisz” woła `projects.rename`, Escape albo „Anuluj” zamyka dialog. Błąd (`InvalidDisplayName`, `StorageFailed`, `UnknownProject`) zostawia dialog z wpisanym tekstem i stałym komunikatem z `ProjectMessages`.
2. **Liczniki (FR-P6).** Przy każdym wierszu: „czeka: n” (wyróżnione) i „pracuje: n” z `SessionsSnapshot.countsFor`. Zera się nie pokazują. Przy `Loading` nie ma liczników. Przy `Stale` widać ostatnie znane liczniki, a oznaczenie nieaktualności pokazuje Mission Control (AM-405).
3. **Usuwanie (FR-P4) przez `SessionCommands.stopAllIn`.** Dialog otwiera się od razu z licznikami ze snapshotu, bez listowania przez runtime. Znika stan `CHECKING_SESSIONS`, `ActiveSessions` (duplikat reguły z `impl`) i zależność `projects:ui` → `agent-runtime:api`.

Nie robimy: wpięcia `sessionsModule` w `app` ani `selection` w kontrolerze (oba robi AM-405), pozycji „Zmień nazwę” w menu okna i palecie (AM-406), zbierania `SessionMonitor.events`, zmian `projects:api` i `sessions:api`, `core:design-system` (AM-802).

## Zmiany API

`projects:api`, `sessions:api`: brak. Publiczne API `projects:ui`: zmienia się tylko konstruktor (jedynym wywołującym jest `app`):

```kotlin
/**
 * State holder of the projects sidebar. Runs every command in [scope] (the window scope, Main dispatcher);
 * at most one dialog flow at a time, further requests are ignored until it ends. Never throws: errors
 * become fixed texts without paths (ENG-C8). Logs only fixed categories, counts, project and session ids.
 *
 * @param sessions read side for the per-project counts, [SessionsApi.commands] for "stop sessions and remove";
 *   only [SessionMonitor.snapshot] is collected (conflated), never [SessionMonitor.events].
 */
public class ProjectsController(
    projects: ProjectsApi, inspector: ProjectInspector, sessions: SessionsApi, picker: DirectoryPicker,
    scope: CoroutineScope, logger: Logger,
)
```

Zostaje sześć parametrów (limit detektu). `SessionsApi` zamiast pary `SessionMonitor` + `SessionCommands` (ENG-I2 dalej spełnione: kontroler czyta `monitor` i `commands` osobno), bo siódmy parametr przekroczyłby limit.

Wewnętrzne (`internal`, KDoc po angielsku):

```kotlin
internal data class ProjectsUiState(/* dotychczasowe pola */ val sessions: SessionsView = SessionsView.Unknown)

/** Per-project counts for the sidebar; [fresh] = from a successful listing (the remove dialog trusts only that). */
internal data class SessionsView(val counts: Map<ProjectId, SessionCounts>, val fresh: Boolean) {
    companion object {
        val Unknown: SessionsView
        /** Pure: Loading → Unknown; Fresh/Stale → countsFor of every listed project with active > 0, fresh = status is Fresh. */
        fun of(projects: List<Project>, snapshot: SessionsSnapshot): SessionsView
    }
}
/** Pure: "czeka: n", "pracuje: n"; zeros and null give no text. */
internal object CountBadges { fun of(counts: SessionCounts?): List<UiText> }
/** Pure: fixed text and log category for a failed stopAllIn; never ids or paths in the text. */
internal object StopMessages { fun of(e: SessionError): UiText; fun category(e: SessionError): String }

// Dialog: ConfirmRemove(project, sessions: List<SessionId>?) → ConfirmRemove(project, active: SessionCounts?)
//   active = null: the snapshot is not Fresh, only "remove from list"; frozen when the dialog opens.
// New: Dialog.Rename(project: Project, draft: String, error: UiText? = null)
// Removed: Dialog.Waiting.CHECKING_SESSIONS
// SidebarEvent new: RenameRequested(id), NameChanged(text), ConfirmRename
```

### Decyzje

1. **Snapshot w kontrolerze.** Dotychczasowy kolektor `projects.projects` zastępuje jeden kolektor `combine(projects.projects, sessions.monitor.snapshot)`, który ustawia `projects` i `sessions = SessionsView.of(…)` w jednym `update`. Oba źródła to `StateFlow`, więc nie ma przeciwciśnienia na pętlę pollingu. Uwaga z AM-403 o `events` nie dotyczy, bo `events` nie zbieramy.
2. **Dialog usuwania** (`RemoveSelectedRequested`) otwiera się synchronicznie i zamraża `active`:

   | Stan sesji przy otwarciu | `active` | Przyciski |
   | --- | --- | --- |
   | snapshot nie jest `Fresh` (`Loading`/`Stale`) | `null` | „Usuń z listy”, „Anuluj” (tekst `remove.sessionsUnknown`: „Stan sesji nie jest znany”) |
   | `Fresh`, 0 aktywnych | `SessionCounts(0,0)` | „Usuń”, „Anuluj” |
   | `Fresh`, n > 0 aktywnych | liczniki | „Zatrzymaj sesje i usuń”, „Usuń z listy, sesje działają dalej”, „Anuluj” |

3. **„Zatrzymaj i usuń”** (tylko przy `active.active > 0`): `BUSY` ustawiamy przed `launch`, potem `commands.stopAllIn(project.id)`. `stopAllIn` sam robi świeży listing, więc zatrzyma też sesję, która ruszyła po otwarciu dialogu. `Ok(n)` → `projects.remove` i log `sessionsStopped = n`. `Err` → projekt **zostaje** (decyzja z AM-304, pyt. 2), `Dialog.Message(StopMessages.of(e))` i WARN z `StopMessages.category(e)`.
4. **Zmiana nazwy.** `RenameRequested(id)` działa tylko bez dialogu. `NameChanged` aktualizuje `draft` i czyści `error`. `ConfirmRename`: `draft.trim()` równy obecnej nazwie zamyka dialog bez zapisu. W pozostałych przypadkach ustawiamy `BUSY`, wołamy `projects.rename(id, draft)`, a potem `Ok` zamyka dialog, a `Err` przywraca `Rename(project, draft, ProjectMessages.of(e))`. Walidacji nie powtarzamy po stronie UI, robi to `ProjectInputRules` w `rename`. Nazwa nigdy nie trafia do logów. Przy otwartym dialogu `menu.canRemove = false`, więc ⌘⌫ trafia do pola.
5. **Teksty** (`projects.properties`): `row.rename`, `row.waiting=czeka: {0}`, `row.working=pracuje: {0}`, `rename.title`, `rename.save`, `remove.runtimeFailed`. Usuwamy `remove.checking`. Wiersz ma semantykę z pełnym opisem liczników dla VoiceOver.

| `StopMessages.of` | Klucz | Kategoria logu |
| --- | --- | --- |
| `StopIncomplete(1, [a])` | `remove.stopFailed` | `stopIncomplete` (+ `failed` = 1) |
| `Runtime(p)` ×6 | `remove.runtimeFailed` | `runtime.<p>` |
| `UnknownProject`, `UnknownSession`, `SessionActive` | `remove.stopFailed` | `unknownProject` / `unknownSession` / `sessionActive` |

## Koordynacja z AM-405

- **Kolejność (rekomendacja):** AM-405 scala się pierwsze, a AM-305 robi rebase i wysyła PR dopiero potem. Commity w `projects:ui` (cała logika i testy) mogą powstać wcześniej, bo nie zależą od `app`. Commit `app` to po rebase jedna linia w `Main.kt`, która zakłada, że AM-405 dał `val sessions: SessionsApi = sessionsModule(…)` na scope z `SupervisorJob`:
  `ProjectsController(projects, inspector, sessions, picker, scope, core.logger)`.
- **Konflikty w `ProjectsController.kt`:** AM-405 dodaje publiczne `selection: StateFlow<ProjectId?>` (addytywnie). AM-305 nie rusza tej właściwości ani `menu` i zmienia tylko parametr `runtime` → `sessions`, blok `init`, `checkSessions`/`remove` i nowe metody na końcu klasy. Konflikt rozwiązuje się ręcznie przy rebase (zachować `selection`). Testy AM-405 dla `selection` przechodzą na `ControllerWorld` z `FakeSessions`.
- **Gdyby AM-305 musiało pójść pierwsze** (pytanie 1): AM-305 dodaje w `app` tylko `sessionsModule(runtime, projects, appScope, core.clock, core.logger)` (`appScope = CoroutineScope(SupervisorJob() + core.dispatchers.main)`) oraz `:feature:sessions:{api,impl}` w `build.gradle.kts`, w tym samym miejscu i z tą samą nazwą `sessions`, którą planuje AM-405. AM-405 przy rebase usuwa wtedy swój duplikat.

## Ryzyka i pytania

Pytania blokujące: brak, pod warunkiem kolejności z sekcji „Koordynacja” (AM-405 pierwsze).

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Kolejność PR.** Rekomendacja: AM-305 po scaleniu AM-405, wtedy w `app` zmienia się jedna linia. Alternatywa (AM-305 pierwsze) jest opisana wyżej i daje konflikt do rozwiązania po stronie AM-405.
2. **Snapshot `Stale`/`Loading` w dialogu usuwania.** Rekomendacja: tylko „Usuń z listy”, bez stopu (jak przy błędzie listingu w AM-304). Alternatywa: zawsze oferować stop, bo `stopAllIn` i tak robi świeży listing, ale przy niedziałającym `claude` skończy się błędem.
3. **Liczniki przy `Stale`.** Rekomendacja: pokazywać ostatnie znane, bez oznaczenia w sidebarze (oznaczenie jest w Mission Control). Alternatywa: przygaszone.
4. **Wejście do zmiany nazwy** tylko z menu ⋯ wiersza. Pozycję w menu okna i komendę palety dokłada AM-406 (wymaga nowego `ProjectsIntent`).

Ryzyka:

- Konflikt w `ProjectsController.kt` i `Main.kt` z AM-405. Ogranicza go zakres zmian opisany w „Koordynacji”.
- Dialog z zamrożonymi licznikami: jeśli sesja ruszy po otwarciu dialogu z 0 aktywnych, „Usuń” zostawi ją działającą (zachowanie domyślne FR-P4). Przy n > 0 `stopAllIn` zatrzyma także nową.
- `stopAllIn` trwa do kilkunastu sekund (listing i `stop` po kolei), a `BUSY` nie da się anulować. Tak samo było w AM-304.
- `BasicTextField` bez Material: Enter i Escape trzeba obsłużyć ręcznie (`onPreviewKeyEvent`/`KeyboardActions`). Sprawdzić ręcznie na Macu razem z ⌘⌫ w polu.
- Rozmiar: ok. 260 linii produkcyjnych netto (kontroler +60/−30, stan i zdarzenia +35, `SessionsView`/`CountBadges`/`StopMessages` ~60, sidebar i liczniki ~45, dialog nazwy ~55, tagi i `app` ~10, usunięcia ~−25). Mieści się w ENG-C10, podział nie jest potrzebny.
