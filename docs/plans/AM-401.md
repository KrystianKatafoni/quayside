# AM-401 · sessions:api (SessionMonitor, SessionCommands) + kontrakty

Issue: #25 · Wymagania: ENG-I1–I8, ENG-T2, ENG-C8 (API pod FR-S1–S4, FR-P4, FR-P6, NFR-2, NFR-3), docs/11 §4, §7 · Etap: M4

## Zakres

Nowy moduł `feature:sessions:api` (skill `/new-module sessions`, tylko część `api`): odczyt stanu sesji (`SessionMonitor`) i komendy (`SessionCommands`), rozdzielone zgodnie z ENG-I2. Żadnej implementacji.

- Typy i interfejsy z KDoc (ENG-I1): `SessionMonitor`, `SessionCommands`, `Session`, `SessionState` (z regułą „aktywna”), `SessionsSnapshot`, `SnapshotStatus`, `SessionCounts`, `SessionEvent`, `NewSessionSpec`, `SessionPermissionMode`, `SessionError`, `RuntimeProblem`, `SessionRules` (czyste przypisanie sesji do projektu).
- `testFixtures`: kontrakty `SessionMonitorContract` i `SessionCommandsContract`, wspólny `SessionsHarness` i `SessionsWorld`, fake `FakeSessions` (jeden stan, implementuje oba interfejsy, ENG-I7), builder `aSession(...)`.
- Wpis `include(":feature:sessions:api")` w `settings.gradle.kts`.

Nie robimy: reducera (AM-402), pollingu (AM-403), komend w `impl` (AM-404), UI (AM-405), scalania z hookami (AM-603), `reply` (FR-S5, patrz pytanie 3) ani zmian w `projects:*` i `agent-runtime:api`.

## Moduły

`feature:sessions:api` (nowy), `settings.gradle.kts`. Opcjonalnie `docs/11-koncepcja-techniczna.md` §4: tylko dopasowanie szkicu do ostatecznego API.

`build.gradle.kts` jak w `projects:api`: `am.feature.api`; `api(project(":core:domain"))`; `testFixturesApi(project(":core:testing"))`; `testFixturesImplementation` JUnit BOM, `junit-jupiter`, `kotest-assertions`, `kotlinx-coroutines-test`. ## Zmiany API

Metody `suspend` można wołać z dowolnego dispatchera, nie blokują wątku (ENG-I5) i nie rzucają wyjątków poza `CancellationException` (ENG-I4). Typy są niemutowalne (ENG-I3).

```kotlin
/** Read side (ENG-I2). Hot; state survives app restarts in the supervisor and is rebuilt on start (NFR-3). */
interface SessionMonitor {
    /** [SessionsSnapshot.Initial] until the first listing; refreshed at least every 3 s (NFR-2). Conflated: UI reads the latest. */
    val snapshot: StateFlow<SessionsSnapshot>
    /** State transitions; hot, no replay. Emitted after [snapshot] already shows [SessionEvent.session]. */
    val events: Flow<SessionEvent>
}

/**
 * One session as Quayside sees it. [summary] (FR-S7) and [cwd] are user data: log at DEBUG only (ENG-C8);
 * `toString` hides [summary].
 * @property project the deepest registered project whose dir contains [cwd] (by path components); null = none.
 * @property lastActivityAt last state change or hook event (FR-S1 "ostatnie zdarzenie i wiek").
 */
data class Session(val id: SessionId, val project: ProjectId?, val name: String, val cwd: Path,
    val state: SessionState, val startedAt: Instant, val lastActivityAt: Instant, val summary: String?)

/** FR-S2. [isActive] is the single "active session" rule: the agent keeps running (supervisor WORKING/BLOCKED). */
sealed interface SessionState {
    val isActive: Boolean          // Working, AwaitingInput, AwaitingPermission
    val isWaiting: Boolean         // AwaitingInput, AwaitingPermission
    data object Working : SessionState
    data class AwaitingInput(val question: String?) : SessionState      // toString hides question
    data class AwaitingPermission(val tool: String?) : SessionState
    data object Done : SessionState
    data object Failed : SessionState
    data object Stopped : SessionState
}

/** [sessions] ordered by startedAt, then id. */
data class SessionsSnapshot(val sessions: List<Session>, val status: SnapshotStatus) {
    /** Pure: active sessions with [Session.project] == [project] (FR-P6, AM-305). */
    fun countsFor(project: ProjectId): SessionCounts
    companion object { val Initial: SessionsSnapshot /* emptyList(), Loading */ }
}
data class SessionCounts(val working: Int, val waiting: Int) { val active: Int get() = working + waiting }
/** docs/11 §7: a failed refresh keeps the last sessions and marks them stale. */
sealed interface SnapshotStatus {
    data object Loading : SnapshotStatus                                 // nothing listed yet
    data class Fresh(val at: Instant) : SnapshotStatus
    data class Stale(val lastFreshAt: Instant?, val problem: RuntimeProblem) : SnapshotStatus
}

/** Transitions only: sessions already present in the first snapshot emit nothing. */
sealed interface SessionEvent {
    val session: Session
    data class BecameBlocked(override val session: Session) : SessionEvent      // → AwaitingInput / AwaitingPermission
    data class TurnFinished(override val session: Session) : SessionEvent       // → Done
    data class Failed(override val session: Session) : SessionEvent             // → Failed
    data class PullRequestReady(override val session: Session) : SessionEvent   // not emitted before its task
    data class RunningLong(override val session: Session, val duration: Duration) : SessionEvent // as above
}

/** Commands (ENG-I2). Every successful command is visible in [SessionMonitor.snapshot] before it returns. */
interface SessionCommands {
    /** FR-S3; runs in the project dir. Errors: UnknownProject, Runtime. The new session is Working. */
    suspend fun start(project: ProjectId, spec: NewSessionSpec): Outcome<SessionId, SessionError>
    /** FR-S4; idempotent: a session that is not active is left as is. Errors: UnknownSession, Runtime. */
    suspend fun stop(id: SessionId): Outcome<Unit, SessionError>
    /**
     * FR-P4: stops every active session attributed to [project] (same rule as [SessionsSnapshot.countsFor]),
     * from a fresh listing, not the possibly stale snapshot. Tries every session; returns how many it stopped.
     * Errors: UnknownProject, StopIncomplete (some stopped, [failed] still running), Runtime (listing failed).
     */
    suspend fun stopAllIn(project: ProjectId): Outcome<Int, SessionError>
    /** Stopped, Done or Failed → Working. Errors: UnknownSession, SessionActive, Runtime. */
    suspend fun respawn(id: SessionId): Outcome<Unit, SessionError>
    /** Removes from the list, never deletes project files. Errors: UnknownSession, SessionActive, Runtime. */
    suspend fun remove(id: SessionId): Outcome<Unit, SessionError>
}

/** FR-S3. Optional texts absent or not blank (init `require`, like `StartSpec`); toString hides [prompt]. */
data class NewSessionSpec(val prompt: String, val name: String? = null, val agent: String? = null,
    val model: String? = null, val permissionMode: SessionPermissionMode? = null)
enum class SessionPermissionMode { DEFAULT, ACCEPT_EDITS, PLAN, BYPASS_PERMISSIONS }

sealed interface SessionError {
    data class UnknownProject(val id: ProjectId) : SessionError
    data class UnknownSession(val id: SessionId) : SessionError
    data class SessionActive(val id: SessionId) : SessionError
    data class StopIncomplete(val stopped: Int, val failed: List<SessionId>) : SessionError
    data class Runtime(val problem: RuntimeProblem) : SessionError
}
/** Fixed categories of runtime failures (1:1 with `RuntimeError` except UnknownSession); no texts (ENG-C8). */
enum class RuntimeProblem { NOT_INSTALLED, UNSUPPORTED_VERSION, AGENT_VIEW_DISABLED, COMMAND_FAILED, UNPARSEABLE, TIMEOUT }
```

Zmiany względem szkicu docs/11: doszły `Session`, `SessionsSnapshot`, `SnapshotStatus`, `SessionCounts`, `NewSessionSpec`, `SessionError`, `RuntimeProblem`, reguła `isActive`/`isWaiting`; `reply` usunięte (pytanie 3).

## Ryzyka i pytania

Pytania blokujące: brak.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Kto podmienia `projects:ui` na `stopAllIn`.** Roadmapa przypisuje to AM-404/405, ale te zadania zmieniają tylko `sessions:impl` i `mission-control:ui`. Rekomendacja: podmiana w AM-305 (już zmienia `projects:ui` i czyta `SessionMonitor`), z dodatkową zależnością AM-305 → AM-404.
2. **Jedno źródło reguły „aktywna”.** `SessionState.isActive` jest źródłem dla wszystkich, którzy widzą `sessions:api`. Kopia w `projects:ui` znika z podmianą (pyt. 1). Kopia w `projects:impl` (`DirectoryInspector`) liczy po `RuntimePhase` katalogu jeszcze niedodanego, więc zostaje; tabela w AM-402 pilnuje `WORKING`/`BLOCKED` ↔ `isActive`. Alternatywa: `RuntimePhase.isActive` w `agent-runtime:api` (zmiana cudzego `api`, osobne zadanie). Rekomendacja: zostawić tak.
3. **`reply` poza `SessionCommands`.** Strategia odpowiedzi jest otwartą kwestią (docs/09), a FR-S5 to „S”. Rekomendacja: później osobny mały interfejs `SessionReplies` (dodanie nie łamie API).
4. **Przypisanie do najgłębszego projektu.** Dziś `listSessions(under = dir)` liczy też sesje w zagnieżdżonym projekcie, więc usunięcie rodzica zatrzymałoby sesje dziecka. Rekomendacja: każda sesja należy do jednego projektu, liczniki się nie dublują, a `stopAllIn` nie rusza sesji projektu, który zostaje.
5. **Brak zdarzeń za stan zastany przy starcie** (NFR-3): sesja, która już czeka, nie daje popupu po ponownym otwarciu aplikacji, tylko licznik i badge ze snapshotu. Rekomendacja: przyjąć.
6. **`remove` i `respawn` aktywnej sesji → `SessionActive`** zamiast niejawnego zatrzymania. Rekomendacja: przyjąć.

Ryzyka:

- FR-S8 (worktree, model, tryb, ostatnie zdarzenia hooków, PR) nie ma pól w `Session`, bo `RuntimeSession` ich nie dostarcza. AM-405 zmienia tylko `mission-control:ui`, więc te pola dojdą zadaniem ze zmianą `sessions:api` (ENG-I6).
- `PullRequestReady` i `RunningLong` są w API z docs/11, ale nic ich jeszcze nie emituje; kontrakt ich nie sprawdza.
- Kontrakt z pollingiem na wirtualnym czasie: `settle()` w impl musi przesunąć czas o interwał, a nie wołać `advanceUntilIdle` (nieskończona pętla).
- ENG-C8: `cwd`, `summary`, `question` to dane użytkownika; KDoc i `toString` jak w `agent-runtime:api`.

## Uwagi dla AM-403/404

- Skutek udanej komendy trzyma overlay na snapshocie, którego starszy listing nie cofa. Zdjęcie overlay nie jest przejściem stanu i nie emituje zdarzenia.
- Idempotentny `stop` sprawdza stan sesji przed `runtime.stop`; nieaktywnej nie zatrzymuje.
- `stopAllIn`: sesja, dla której runtime zwraca `RuntimeError.UnknownSession`, liczy się jako nieaktywna, nie jako `failed`.
- `stopAllIn` publikuje świeży listing w snapshot przed powrotem.
- AM-305: liczba z `countsFor` (dialog) może różnić się od `Ok(n)` z `stopAllIn`, bo ta liczy ze świeżego listingu.
- AM-305: przy `Err(SessionError.Runtime)` ścieżka „usuń bez zatrzymywania” dalej działa.
