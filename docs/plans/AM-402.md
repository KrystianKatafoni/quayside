# AM-402 · SessionStateReducer (czysty, tablicowe testy)

Issue: #26 · Wymagania: FR-S2 (pod FR-S1, FR-N1, NFR-2, NFR-3), ENG-C9, ENG-T1, docs/05 „Stany sesji”, docs/11 §4, §7, docs/12 §1 · Etap: M4

## Zakres

Nowy moduł `feature:sessions:impl` (skill `/new-module sessions impl`) z czystym rdzeniem: `SessionStateReducer` (poprzedni snapshot + wynik listingu + mapa projektów + czas → nowy `SessionsSnapshot` i lista `SessionEvent`) oraz mapowania `RuntimeSession` → `SessionState` i `RuntimeError` → `RuntimeProblem`. Wszystko `internal`, bez IO, bez zegara, bez korutyn.

Nie robimy: pętli pollingu, `Clock`, `StateFlow` i `SessionMonitor` (AM-403), komend i overlay (AM-404), hooków (AM-603), podsumowań (AM-604), wpięcia w `app`, zmian `sessions:api` i `agent-runtime:api`.

**Bez fabryki modułu.** Fabryka z docs/11 (`sessionsModule(core, runtime, projects, summaries)`) zwraca monitor i komendy; w AM-402 nie istnieje żadne z nich, więc fabryka byłaby atrapą w kodzie produkcyjnym (rzucająca `TODO` albo kłamiąca pustym snapshotem), której nic nie woła. Szablon `/new-module` (`Default…Api`) pomijamy w całości; fabrykę dodaje AM-403 razem z `SessionMonitor` (pytanie 5). Moduł nie ma żadnej deklaracji publicznej, co Konsist (`impl exposes only its module factory`) przepuszcza.

## Zmiany API

`sessions:api`, `agent-runtime:api`: brak. Wewnętrzne (KDoc po angielsku):

```kotlin
/** Result of one [SessionStateReducer.reduce]: publish [snapshot] first, then [events] (AM-401 contract). */
internal data class Reduction(val snapshot: SessionsSnapshot, val events: List<SessionEvent>)

/** Pure core of the sessions feature (docs/11 §7). Stateless; no IO, no clock, never throws. */
internal object SessionStateReducer {
    /**
     * @param previous the snapshot published so far ([SessionsSnapshot.Initial] on start).
     * @param listing result of `AgentRuntime.listSessions()`; AM-404 passes it through its command overlay first.
     * @param projects registered project dirs for [SessionRules.projectFor].
     * @param now time of the listing (from the injected `Clock` in AM-403).
     * @return sessions ordered by startedAt, then id; events in the same order, only for transitions.
     */
    fun reduce(previous: SessionsSnapshot, listing: Outcome<List<RuntimeSession>, RuntimeError>,
               projects: Map<ProjectId, Path>, now: Instant): Reduction
}

/** FR-S2, docs/05: supervisor phase and waiting reason → state. Details (question, tool) come with hooks (AM-603). */
internal fun RuntimeSession.toSessionState(): SessionState
/** Fixed category of a listing failure (ENG-C8: drops exit codes, tails and details). */
internal fun RuntimeError.toProblem(): RuntimeProblem
```

### Reguły reducera

1. **Linia bazowa** (NFR-3, AM-401 pyt. 5): gdy `previous` nie ma udanego listingu (`Loading` albo `Stale(lastFreshAt = null)`), pierwszy udany listing nie emituje zdarzeń, a `lastActivityAt = startedAt` (lepszej wiedzy brak do AM-603).
2. **Udany listing**: `status = Fresh(now)`; każda sesja z listingu, `project = SessionRules.projectFor(cwd, projects)` liczone za każdym razem (zmiana projektów przepina sesje bez zdarzeń); `name`, `cwd`, `startedAt` z listingu; `summary` z poprzedniej wersji sesji (dziś zawsze `null`). Sesja nieobecna w listingu znika bez zdarzenia. Powtórzone `id` w listingu: wygrywa pierwsze wystąpienie.
3. **`lastActivityAt`**: nowa sesja po linii bazowej → `now`; stan różny (`!=`) od poprzedniego → `now`; inaczej poprzednia wartość.
4. **Zdarzenia** tylko przy zmianie *rodzaju* stanu (Working, AwaitingInput, AwaitingPermission, Done, Failed, Stopped), nie szczegółów (`question`, `tool`), więc późniejsze dołożenie szczegółów przez hooki nie daje fałszywego przejścia. Brak sesji wcześniej (po linii bazowej) liczy się jako rodzaj „brak”. Nowy rodzaj → zdarzenie: AwaitingInput/AwaitingPermission → `BecameBlocked`, Done → `TurnFinished`, Failed → `Failed`, Working/Stopped → nic. `PullRequestReady`, `RunningLong` nigdy.
5. **Błąd listingu** (docs/11 §7): sesje zostają, `project` przeliczone wg bieżących `projects`, stany i `lastActivityAt` bez zmian, zero zdarzeń; `status = Stale(lastFreshAt, error.toProblem())`, gdzie `lastFreshAt` = `Fresh.at` albo `Stale.lastFreshAt` z `previous` (`null` z `Loading`). Powrót po błędzie porównuje z ostatnimi znanymi sesjami, więc przejścia z czasu awarii dają zdarzenia.
6. **Overlay komend (AM-404)** nie wchodzi do reducera: AM-404 doda czystą funkcję nakładającą skutki komend na `List<RuntimeSession>` przed `reduce`. Zdjęcie overlay, gdy listing potwierdzi skutek, nie zmienia rodzaju stanu, więc nie emituje zdarzenia; skutki komend (Stopped, Working, zniknięcie) i tak nie są zdarzeniami. Hooki (AM-603) rozszerzą sygnaturę `internal` o drugie wejście.

| `RuntimeSession` (`phase` / `waitingFor`) | `toSessionState()` |
| --- | --- |
| `WORKING` / dowolne | `Working` |
| `BLOCKED` / `Permission` | `AwaitingPermission(null)` |
| `BLOCKED` / `Input`, `Other("x")`, `null` | `AwaitingInput(null)` |
| `DONE`, `FAILED`, `STOPPED` / dowolne | `Done`, `Failed`, `Stopped` |

| `RuntimeError` | `toProblem()` |
| --- | --- |
| `NotInstalled`, `UnsupportedVersion`, `AgentViewDisabled`, `Timeout` | `NOT_INSTALLED`, `UNSUPPORTED_VERSION`, `AGENT_VIEW_DISABLED`, `TIMEOUT` |
| `CommandFailed(1, "tail")`, `Unparseable("x")` | `COMMAND_FAILED`, `UNPARSEABLE` |
| `UnknownSession(id)` (listing go nie zwraca) | `COMMAND_FAILED` |

## Ryzyka i pytania

Uwagi z review dla AM-403/404 i AM-603:

- `lastActivityAt` porównuje pełny stan. Gdy hooki (AM-603) zaczną dostarczać `question`/`tool`, trzeba je scalić z listingiem przed `reduce`, inaczej każdy listing bez szczegółów przesunie „ostatnią aktywność” na `now`.
- Wywołania `reduce` z pętli pollingu i z komend muszą być serializowane (jeden wątek albo `Mutex`), bo równoległe czytanie `previous` gubi wynik jednej ze stron.
- Skutek komendy (np. `start`) nie powinien przechodzić przez `reduce` jako udawany listing, bo dałby fałszywe `Fresh(now)`; overlay nakłada AM-404 osobno, z przeliczeniem projektu przez `SessionRules.projectFor`.

Pytania blokujące: brak.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **`WaitingFor.Other` i `BLOCKED` bez powodu → `AwaitingInput`.** Sesja i tak czeka na człowieka; „prosi o zgodę” tylko przy jawnym `Permission`. Rekomendacja: przyjąć.
2. **Sesja pojawiająca się po starcie już w Done/Failed emituje `TurnFinished`/`Failed`**, analogicznie do „pojawia się czekająca → `BecameBlocked`” z AM-401 (pojawienie się = przejście z „brak”). Alternatywa: zdarzenie tylko dla czekającej. Rekomendacja: przyjąć.
3. **Input ↔ Permission bez Working pomiędzy daje ponowne `BecameBlocked`** (inne pytanie do użytkownika), a zmiana samych szczegółów nie. Rekomendacja: przyjąć.
4. **`lastActivityAt = startedAt` dla sesji zastanych przy starcie**: wiek „ostatniego zdarzenia” (FR-S1) może być zawyżony do AM-603. Alternatywa `now` zaniża go. Rekomendacja: `startedAt`.
5. **Typ zwracany fabryki w AM-403.** docs/11 zakłada `SessionsApi(monitor, commands)`, ale takiego typu nie ma w `sessions:api` (PR #76), a publiczna klasa w `impl` łamie regułę Konsist. AM-403 będzie musiało albo dodać `SessionsApi` do `sessions:api` (zmiana scalonego `api` = decyzja człowieka), albo mieć dwie fabryki / jeden obiekt implementujący oba interfejsy zwracany jako `SessionMonitor` i `SessionCommands`. Nie blokuje AM-402 (brak fabryki); warto zdecydować przed planem AM-403.
6. **`RuntimeError.UnknownSession` → `COMMAND_FAILED`** w mapowaniu, bo `RuntimeProblem` nie ma tej kategorii z założenia (AM-401). Komendy w AM-404 obsłużą `UnknownSession` przed mapowaniem (→ `SessionError.UnknownSession`).

Ryzyka:

- Polling co ≤ 3 s gubi krótkie stany (Working → Done → Working między listingami = brak `TurnFinished`); naprawia to scalanie z hookami (AM-603), nie reducer.
- Linia bazowa zależy od `previous.status`: jeśli AM-403 kiedykolwiek wróci do `Initial` (np. restart pętli), zdarzenia za stan zastany zostaną stłumione drugi raz, co jest zamierzone; ale zdarzenia z tego okna przepadną.
- Reducer nie loguje: `cwd`, `name`, `question` to dane użytkownika (ENG-C8); logowanie zostaje w AM-403 z samymi `SessionId`.
- PR mały: ok. 120 linii kodu produkcyjnego, poniżej limitu ENG-C10.
