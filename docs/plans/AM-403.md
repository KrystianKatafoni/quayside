# AM-403 · Pętla pollingu + snapshot

Issue: #27 · Wymagania: FR-S1, NFR-2, NFR-3 (pod ENG-C6, ENG-C8, ENG-C9, ENG-T2), docs/11 §6, §7, ADR 0004 · Etap: M4

## Zakres

Implementacja `SessionMonitor` w `sessions:impl`: pętla `AgentRuntime.listSessions()` w wstrzykniętym `CoroutineScope`, publikacja `snapshot` i `events` przez `SessionStateReducer` (AM-402), ponowienia z backoffem przy błędach (snapshot `Stale`), natychmiastowy listing po zmianie mapy projektów, fabryka modułu zwracająca `SessionMonitor`. Kontrakt `SessionMonitorContract` uruchomiony na prawdziwej implementacji.

Nie robimy: komend i overlay (AM-404), scalania z hookami i `lastActivityAt` z hooków (AM-603), podsumowań (AM-604), wpięcia w `app` (pytanie 4), zmian `sessions:api` main, `agent-runtime:api`, `projects:api`.

## Moduły

- `feature:sessions:impl`: `build.gradle.kts` + `implementation(project(":feature:projects:api"))` (`ProjectsApi`, `Project`); `testImplementation(testFixtures(project(":feature:projects:api")))` (`FakeProjectsApi`). Coroutines są w `api` z `core:domain`, `kotlinx-coroutines-test` daje `am.kotlin`. Bez nowych bibliotek, bez ADR. Komentarz w nagłówku pliku poprawić („factory comes with AM-403” → opis fabryki).
- `feature:sessions:api`, **tylko `src/testFixtures`** (`SessionMonitorContract`), wyłącznie jeśli człowiek przyjmie rekomendację pytania blokującego 2.
- Opcjonalnie `docs/11-koncepcja-techniczna.md` §9: jedno zdanie o fabryce (pytanie 1).

## Zmiany API

`sessions:api` (main), `agent-runtime:api`, `projects:api`: brak. Publiczna jest tylko fabryka (Konsist `impl exposes only its module factory`); wzorzec: dwie fabryki `projects:impl` (`projectsModule`, `projectInspectorModule`), każda zwraca jeden interfejs `api`.

```kotlin
/**
 * Starts watching the supervisor in [scope] and returns the read side of sessions (FR-S1, NFR-2, NFR-3).
 * The first listing runs at once, then one every [pollInterval] after the previous one ends; a change of
 * the project dirs in [projects] lists again at once. After repeated failures the wait grows up to
 * [maxRetryInterval] while the snapshot stays [SnapshotStatus.Stale]. Cancelling [scope] stops polling; the
 * last snapshot stays readable. Not suspending: the snapshot is [SessionsSnapshot.Initial] until the first
 * listing. The long parameter list is deliberate: `impl` may expose only factories.
 *
 * @param scope owner of the loop, e.g. the app scope with a SupervisorJob; tests pass `backgroundScope`.
 * @param clock time of each listing ([SnapshotStatus.Fresh.at], `lastActivityAt`).
 * @param logger gets session ids, counts and [RuntimeProblem] only, never cwd, names or questions (ENG-C8).
 * @throws IllegalArgumentException if [pollInterval] is not positive or [maxRetryInterval] is shorter.
 */
@Suppress("LongParameterList")
public fun sessionMonitorModule(
    runtime: AgentRuntime,
    projects: ProjectsApi,
    scope: CoroutineScope,
    clock: Clock,
    logger: Logger,
    pollInterval: Duration = 2.seconds,
    maxRetryInterval: Duration = 15.seconds,
): SessionMonitor
```

Fabryka rzuca `IllegalArgumentException` wyłącznie przy błędnej konfiguracji interwałów (`pollInterval` niedodatni albo `maxRetryInterval < pollInterval`; błąd programisty, `require` w `PollSchedule`); poza tym nie rzuca.

Wewnętrzne (KDoc po angielsku, wszystko `internal`):

```kotlin
/** Pure (ENG-C9): wait before the next listing. Up to [GRACE_FAILURES] failures in a row keep [interval]. */
internal data class PollSchedule(val interval: Duration, val maxRetryInterval: Duration) {
    init { require(interval.isPositive() && maxRetryInterval >= interval) }
    fun delayAfter(consecutiveFailures: Int): Duration   // never overflows, never above maxRetryInterval
}

/**
 * Single owner of the published state. [publish] reads the current snapshot, reduces, sets [snapshot],
 * then emits the events, all under one Mutex (AM-402 review: calls of reduce are serialized). AM-404
 * commands publish through the same instance.
 */
internal class SessionsState(private val clock: Clock) {
    val snapshot: StateFlow<SessionsSnapshot>           // MutableStateFlow(Initial)
    val events: SharedFlow<SessionEvent>                // replay 0, extraBufferCapacity 64 (docs/11 §6)
    suspend fun publish(listing: Outcome<List<RuntimeSession>, RuntimeError>, projects: Map<ProjectId, Path>): Reduction
}

/** The polling loop (docs/11 §6, §7); [start] launches it and the project watcher in the given scope. */
internal class PollingSessionMonitor(
    private val runtime: AgentRuntime, private val projects: ProjectsApi, private val state: SessionsState,
    private val schedule: PollSchedule, private val logger: Logger,
) : SessionMonitor {
    fun start(scope: CoroutineScope)
}
```

### Reguły pętli

1. Listing zawsze `listSessions(under = null)`; mapa projektów `projects.projects.value.associate { it.id to it.dir }` czytana przy każdym listingu, wynik idzie do `SessionsState.publish`. Żadnego „udawanego listingu” (AM-402 review).
2. Oczekiwanie: `withTimeoutOrNull(schedule.delayAfter(failures)) { wakeups.receive() }` na `Channel<Unit>(CONFLATED)`. Watcher: `projects.projects.map { mapa }.distinctUntilChanged().drop(1)` → `trySend(Unit)`. Zmiana nazwy projektu nie budzi pętli; zmiana w trakcie listingu daje kolejny listing zaraz po nim.
3. `failures` rośnie przy `Err`, zeruje się przy `Ok`. Zmiana projektów nie zeruje licznika.
4. Logi: WARN raz przy przejściu w `Stale` (pole `problem`), INFO raz przy powrocie do `Fresh`, DEBUG liczba sesji. Bez `cwd`, `name`, `question` (ENG-C8).
5. Pętla nie łapie wyjątków (runtime ich nie rzuca, ENG-I4; wyjątek = bug), `CancellationException` przechodzi.

| `delayAfter(n)` przy `interval = 2 s`, `max = 15 s` | Oczekiwane |
| --- | --- |
| 0, 1, 2 | 2 s |
| 3 / 4 | 4 s / 8 s |
| 5, 100, `Int.MAX_VALUE` | 15 s |
| `interval = max = 2 s`, n = 10 | 2 s |
| `interval = 0`, `max < interval` | `IllegalArgumentException` (init) |

## Testy

Wszystkie na `runTest`: pętla w `backgroundScope`, czas przez `advanceTimeBy` + `runCurrent`, nigdy `advanceUntilIdle`. Zegar testowy związany z wirtualnym czasem: `Clock { T0.plusMillis(testScheduler.currentTime) }` (helper `virtualClock()` w testach), więc `Fresh.at` i `lastFreshAt` są sprawdzalne. `FakeAgentRuntime` + `FakeProjectsApi` z testFixtures, `RecordingLogger` z `core:testing`.

- [ ] jednostkowe tablicowe `PollScheduleTest`: `waits the poll interval after up to two failures`, `doubles the wait after repeated failures`, `never waits longer than the maximum`, `rejects invalid intervals` (tabela wyżej).
- [ ] jednostkowe `SessionsStateTest`: `starts with the initial snapshot`, `publishes the snapshot before the events`, `failed listing publishes no events`, `events are not replayed to late collectors`, `fresh time comes from the clock`.
- [ ] jednostkowe `PollingSessionMonitorTest`: `snapshot is loading until the first listing`, `first listing runs at once`, `lists again every poll interval`, `refresh interval stays within three seconds` (NFR-2: domyślne `pollInterval` ≤ 3 s, 3 listingi w 6 s), `restart rebuilds the state from the listing without events` (NFR-3: nowy monitor na tym samym runtime z sesjami czekającymi → pełny snapshot, zero zdarzeń), `failed listing marks the snapshot stale at once`, `retries at the poll interval after one failure`, `backs off after repeated failures`, `success resets the backoff`, `adding a project lists again at once and attributes its sessions`, `removing a project detaches its sessions at once`, `renaming a project does not list again`, `project change while the runtime is down re-attributes stale sessions`, `cancelling the scope stops polling and keeps the last snapshot`, `logs the stale transition once with the problem only`, `logs recovery once`, `logs never contain cwd or session names`.
- [ ] kontraktowe `PollingSessionMonitorContractTest : SessionMonitorContract()`; harness testowy `PollingHarness` w `sessions:impl/src/test`: `SessionsWorld` → `FakeProjectsApi(projekty z displayName = id)` + `FakeAgentRuntime(RuntimeWorld(…))` owinięty testowym `SwitchableRuntime` (gdy wyłączony, każda operacja `Err(NotInstalled)`; `FakeAgentRuntime.failNext` działa tylko raz). `change`/`appear` mapują `SessionState` → `RuntimePhase`/`WaitingFor` (odwrotność tabeli z AM-402), `settle()` = `advanceTimeBy(pollInterval)` + `runCurrent()`. `commands` i `failStop` rzucają `UnsupportedOperationException("AM-404")`: kontrakt monitora ich nie używa, kontrakt komend dochodzi w AM-404.

## Ryzyka i pytania

Pytania blokujące (decyzja człowieka przed startem; plan przyjmuje rekomendacje, które nie zmieniają `sessions:api` main):

1. **Co zwraca fabryka `sessions`.** docs/11 §9 zakłada `SessionsApi(monitor, commands)`, którego nie ma w scalonym `sessions:api`; publiczny typ w `impl` łamie Konsist, a fabryka nie może zwrócić typu `internal`.
   - a) **(rekomendacja)** AM-403: `sessionMonitorModule(…): SessionMonitor`, jak `projectInspectorModule`. AM-404 zmienia fabrykę (to `impl`, nie `api`; nikt jej jeszcze nie woła poza testami): wspólne `SessionsState` dla obu stron i decyzja o typie zwracanym podejmowana w planie AM-404, gdy `SessionCommands` istnieje (np. `SessionsApi` w `sessions:api` albo druga fabryka przyjmująca ten sam stan).
   - b) Dodać teraz `data class SessionsApi(val monitor: SessionMonitor, val commands: SessionCommands)` do `sessions:api`: zmiana scalonego `api` (ENG-I6), a w AM-403 `commands` byłoby atrapą zwracającą błędy albo rzucającą `TODO` w kodzie produkcyjnym. Odradzam.
   - c) Jedna klasa implementująca oba interfejsy zwracana jako `SessionMonitor` i rzutowana w `app`: ukryta zależność od typu, odradzam.
2. **Kontrakt monitora wymaga szczegółów stanu, których polling nie daje.** `becoming blocked emits BecameBlocked`, `permission request emits BecameBlocked` i `session appearing while waiting emits BecameBlocked` sprawdzają `AwaitingInput("Which file?")` / `AwaitingPermission("Bash")`, a z listingu wychodzi `question = null` / `tool = null` (AM-402, szczegóły z hooków w AM-603). Na impl te 3 testy nie przejdą, a metod kontraktu nie da się nadpisać ani wyłączyć w podklasie.
   - a) **(rekomendacja)** Zmiana tylko w `sessions:api/src/testFixtures`: w tych 3 testach asercja rodzaju (`shouldBeInstanceOf<AwaitingInput>()` / `<AwaitingPermission>()`) zamiast pełnej równości; zgodność szczegółów wraca jako osobny test kontraktowy w AM-603. Fake dalej przechodzi; `main` bez zmian. Wymaga dopisania `sessions:api` (testFixtures) do modułów zadania.
   - b) Kontrakt na impl dopiero w AM-603, w AM-403 tylko testy jednostkowe monitora: łamie DoD („każdy interfejs `api` test kontraktowy”), odradzam.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Interwał i backoff:** `pollInterval = 2 s` (docs/11 §6: 2–3 s; czas listingu doliczany, więc ≤ 3 s przy listingu < 1 s), dwa nieudane listingi bez wydłużania, potem 4, 8, do 15 s. Skutek: po naprawie Claude Code (np. włączeniu Agent View) snapshot wraca do `Fresh` po ≤ 15 s. Rekomendacja: przyjąć; ręczne „odśwież” ewentualnie w UI później.
2. **Wpięcie w `app`:** fabryka powstaje bez wywołania w `app`, bo nic jeszcze nie czyta snapshotu, a pętla bez konsumenta uruchamiałaby `claude agents` co 2 s. Rekomendacja: wpięcie z pierwszym konsumentem (AM-305 ma `app` w modułach; AM-405 musi go dopisać).

Ryzyka:

- Wyjątek, który przecieknie z runtime'u, zabija pętlę i (bez `SupervisorJob`) scope rodzica; `app` musi dać scope z `SupervisorJob`. Snapshot zostaje wtedy zamrożony jako `Fresh` z przeszłości; KDoc fabryki to opisuje.
- `extraBufferCapacity = 64`: wolny kolektor zdarzeń spowalnia publikację (emit pod mutexem), nie gubi zdarzeń. Akceptowalne przy kilkunastu sesjach.
- Zmiana projektów w trakcie backoffu wymusza listing (sprawdzenie, czy runtime wrócił); przy częstych zmianach to dodatkowe wywołania `claude`, nieistotne przy ręcznym dodawaniu projektów.
- Emit zdarzeń odbywa się pod mutexem po ustawieniu snapshotu: kolektor, który przestanie zbierać przy pełnym buforze (64), wstrzymuje też aktualizacje snapshotu. Konsumenci (AM-405) nie powinni zbierać `events` na wątku, który może stanąć.
- Rozmiar: ok. 200 linii kodu produkcyjnego (fabryka ~30, `PollSchedule` ~25, `SessionsState` ~50, pętla ~90), poniżej ENG-C10.

Uwagi dla kolejnych zadań (AM-404, AM-405):

- `app` musi przekazać fabryce scope z `SupervisorJob`, inaczej wyjątek z pętli anuluje rodzica.
- Wyjątek z runtime'u kończy pętlę i snapshot zostaje zamrożony (ostatni `Fresh` albo `Stale`), bez sygnału dla UI. Rozważyć przejście w `Stale` przy śmierci pętli (np. `invokeOnCompletion` z przyczyną inną niż anulowanie) w AM-404 albo AM-405.
