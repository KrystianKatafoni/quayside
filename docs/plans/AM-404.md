# AM-404 · Komendy: start, stop, respawn, remove, stopAllIn

Issue: #28 · Wymagania: FR-S3, FR-S4, FR-P4 (pod ENG-I2, ENG-I4, ENG-C6, ENG-C8, ENG-C9, ENG-T2), docs/11 §4, §7, §9 · Etap: M4

## Zakres

`SessionCommands` w `sessions:impl` na bazie `AgentRuntime`, na tym samym `SessionsState` co monitor z AM-403. Po każdej komendzie odświeżamy prawdziwym listingiem. Nakładka skutków komend (AM-401/402) trzyma skutek, dopóki supervisor go nie pokaże, więc starszy listing go nie cofa. Błędy runtime'u mapujemy na `SessionError`, `stop` jest idempotentny, `stopAllIn` liczy sesje ze świeżego listingu. Fabryka zwraca obie strony (pytanie blokujące 1). Kontrakty `SessionCommandsContract` i `SessionMonitorContract` uruchamiamy na impl. `PollingHarness` nie rzuca już `UnsupportedOperationException`.

Nie robimy: `reply` (FR-S5), hooków (AM-603), wpięcia w `app` i podmiany `projects:ui` na `stopAllIn` (AM-305), przejścia w `Stale` przy śmierci pętli (pytanie 2), zmian `agent-runtime:api` i `projects:api`.

## Moduły

- `feature:sessions:impl`: komendy, nakładka, `SessionsState`, fabryka, testy, komentarz w `build.gradle.kts`. Bez nowych zależności i bibliotek, bez ADR.
- `feature:sessions:api`, **tylko jeśli człowiek przyjmie wariant 1a**: nowy plik `SessionsApi.kt` w `main` (zmiana addytywna). `testFixtures` bez zmian.

## Zmiany API

Wariant 1a (`sessions:api`, `main`):

```kotlin
/** Both sides of the sessions feature as returned by `sessionsModule` (docs/11 §9); [commands] publish into [monitor]. */
public data class SessionsApi(val monitor: SessionMonitor, val commands: SessionCommands)
```

Fabryka (`sessions:impl`) zastępuje `sessionMonitorModule`. Ma te same parametry i reguły co w AM-403; dotąd woła ją tylko `PollingHarness`:

```kotlin
/**
 * Starts watching the supervisor in [scope] and returns both sides of sessions over one state (FR-S1, FR-S3,
 * FR-S4). Every successful command is in [SessionMonitor.snapshot] before it returns, from a real listing with
 * the command's effect laid over it until the supervisor reports it (at most COMMAND_OVERLAY_TTL = 10 s).
 * Commands never throw; [logger] gets session ids, counts and [RuntimeProblem] only (ENG-C8).
 * @throws IllegalArgumentException if [pollInterval] is not positive or [maxRetryInterval] is shorter.
 */
@Suppress("LongParameterList")
public fun sessionsModule(runtime: AgentRuntime, projects: ProjectsApi, scope: CoroutineScope, clock: Clock,
    logger: Logger, pollInterval: Duration = 2.seconds, maxRetryInterval: Duration = 15.seconds): SessionsApi
```

Elementy wewnętrzne (wszystko `internal`, KDoc po angielsku):

```kotlin
/** Effect of a successful command the supervisor may not list yet. */
internal sealed interface Expected {
    val id: SessionId; val until: Instant
    data class Appears(val session: RuntimeSession, override val until: Instant) : Expected      // start
    data class Moves(override val id: SessionId, val from: RuntimePhase, val to: RuntimePhase,
                     override val until: Instant) : Expected                                       // stop, respawn
    data class Disappears(override val id: SessionId, override val until: Instant) : Expected      // remove
}
internal data class Overlaid(val sessions: List<RuntimeSession>, val pending: List<Expected>)
/** Pure (ENG-C9): lays [pending] over a successful listing; drops confirmed, contradicted and expired ones. */
internal object CommandOverlay { fun apply(listing: List<RuntimeSession>, pending: List<Expected>, now: Instant): Overlaid }

/** Owner of the published state; now also owns the listing, so list + overlay + reduce + publish are atomic. */
internal class SessionsState(runtime: AgentRuntime, projects: ProjectsApi, clock: Clock, overlayTtl: Duration) {
    val snapshot: StateFlow<SessionsSnapshot>; val events: SharedFlow<SessionEvent>
    /** Adds [expect], then lists, overlays, reduces and publishes under one Mutex. Err = the listing's error. */
    suspend fun refresh(expect: List<Expected> = emptyList()): Outcome<SessionsSnapshot, RuntimeError>
    fun expiry(): Instant                                   // clock.now() + overlayTtl
}
internal class RuntimeSessionCommands(runtime: AgentRuntime, projects: ProjectsApi, state: SessionsState,
    clock: Clock, logger: Logger) : SessionCommands
internal fun NewSessionSpec.toStartSpec(cwd: Path): StartSpec        // 1:1, SessionPermissionMode → PermissionMode
```

`PollingSessionMonitor` woła `state.refresh()` zamiast `listSessions` + `publish`, a liczy błędy na podstawie zwróconego `Outcome`. `publish` znika, a `SessionsStateTest` przechodzi na `refresh`.

### Reguły komend

1. **Walidacja specyfikacji.** Niezmienniki `NewSessionSpec` pilnuje jej `init`. `StartSpec` ma identyczne niezmienniki, więc `toStartSpec` nigdy nie rzuca. `start` bierze katalog z `projects.projects.value`; brak projektu daje `UnknownProject`, a runtime nie jest wtedy wołany.
2. **Wstępna kontrola** `stop`/`respawn`/`remove` to `refresh()` (prawdziwy listing, opublikowany). Błąd listingu daje `Runtime(problem)`, komenda się nie wykonuje.

   | Komenda | Brak sesji | Sesja nieaktywna | Sesja aktywna |
   | --- | --- | --- | --- |
   | `stop` | `UnknownSession` | `Ok`, bez `runtime.stop` | `runtime.stop`, potem `Moves(→STOPPED)` |
   | `respawn` | `UnknownSession` | `runtime.respawn`, potem `Moves(→WORKING)` | `SessionActive` |
   | `remove` | `UnknownSession` | `runtime.rm`, potem `Disappears` | `SessionActive` |

3. **Po udanej operacji** wołamy `refresh(expect)`. Jeśli ten listing się nie uda, komenda i tak zwraca `Ok` (skutek nastąpił), a snapshot jest `Stale`; oczekiwanie zostaje do następnego udanego listingu.
4. **`stopAllIn(p)`**: nieznany `p` daje `UnknownProject`. Potem `refresh()`; przy `Err` zwracamy `Runtime`. Cele to sesje z `project == p && state.isActive` (reguła `countsFor`, z nakładką). Dla każdej wołamy `runtime.stop`: `Ok` zwiększa licznik zatrzymanych, `Err(UnknownSession)` traktujemy jak sesję nieaktywną, każdy inny błąd trafia do `failed`. Na koniec jeden `refresh(expect)` z `Moves` dla zatrzymanych. Wynik: `Ok(n)` albo `StopIncomplete(n, failed)`.
5. **Mapowanie błędów**: `RuntimeError.UnknownSession(id)` daje `SessionError.UnknownSession(id)`, pozostałe błędy dają `Runtime(error.toProblem())` (AM-402).
6. **Logi**: INFO z id sesji i nazwą komendy, WARN z polem `problem`. Nigdy prompt, nazwa ani `cwd`.

| `CommandOverlay.apply`: oczekiwanie / listing | Wynik |
| --- | --- |
| `Appears(s)` / brak `s.id` | `s` dodana, oczekiwanie zostaje |
| `Appears(s)` / `s.id` jest | wygrywa listing, oczekiwanie usunięte |
| `Moves(id, from = WORKING, to = STOPPED)` / `id` w `WORKING` | `STOPPED`, `waitingFor = null`, zostaje |
| `Moves(…)` / `id` w fazie innej niż `from` | wygrywa listing (potwierdzone albo agent poszedł dalej), usunięte |
| `Moves(…)` / brak `id` | usunięte |
| `Disappears(id)` / `id` jest / brak | ukryta, zostaje / usunięte |
| dowolne, `now >= until` | wygrywa listing, usunięte |
| dwa oczekiwania dla jednego `id` | obowiązuje nowsze |
| `Appears(s)`, potem `Moves(s.id, to = …)` / brak `s.id` | zostaje `Appears(s)` w fazie `to`, `waitingFor = null` |

## Ryzyka i pytania

Pytania blokujące (decyzja człowieka przed startem):

1. **Co zwraca fabryka `sessions`.** Funkcja publiczna nie może zwrócić typu `internal`, a Konsist zabrania publicznych klas w `impl`.
   - a) **(rekomendacja)** `data class SessionsApi(monitor, commands)` w `sessions:api` main i `sessionsModule(…): SessionsApi`. Zgodne z docs/11 §9 i ENG-I2 (interfejsy dalej osobno). Zmiana jest addytywna i dotyczy `api` własnego feature, ale to zmiana scalonego `api`: do modułów zadania dochodzi `sessions:api`.
   - b) `sessionsModule(…): Pair<SessionMonitor, SessionCommands>` (`val (monitor, commands) = …`). Bez zmiany `api`, ale typ jest anonimowy i odbiega od docs/11 §9. Wariant zapasowy, jeśli a) zostanie odrzucone.
   - c) Interfejs `SessionsApi : SessionMonitor, SessionCommands` w `api` łamie ENG-I2. Odradzam. Dwie fabryki ze wspólnym stanem są niemożliwe bez publicznego typu stanu.

Pytania do człowieka (niczego nie blokują, plan przyjmuje rekomendację):

1. **Śmierć pętli → `Stale`.** `Stale` wymaga `RuntimeProblem`, a żadna kategoria nie pasuje do błędu programu. Nowa wartość enuma (np. `MONITOR_STOPPED`) to zmiana `api` i `when` u konsumentów (AM-405). Rekomendacja: poza AM-404; osobne małe zadanie albo AM-405 ze zmianą `sessions:api`. Do tego czasu KDoc fabryki opisuje zamrożony snapshot.
2. **Nakładka i TTL 10 s.** Nie wiadomo, czy `claude agents` od razu pokazuje skutek `--bg`/`stop`/`rm`. Bez nakładki kontrakt („widoczne przed powrotem”) mógłby nie przejść na prawdziwym CLI. Jeśli supervisor nie wykona skutku, po 10 s wygrywa listing. Rekomendacja: przyjąć; sprawdzić w AM-904 i ewentualnie usunąć nakładkę później.
3. **Dwa listingi na komendę** (kontrola wstępna i odświeżenie), czyli trzy wywołania `claude`. Kontrola ze snapshotu byłaby szybsza, ale mogłaby nie widzieć świeżo pojawionej sesji. Rekomendacja: świeży listing.

Ryzyka:

- `refresh` trzyma mutex przez cały listing (do 10 s timeoutu CLI), więc komenda czeka na trwający listing pętli. To cena kolejności: żaden starszy listing nie nadpisze nowszego.
- Ten sam mutex obejmuje emit zdarzeń. Zablokowany kolektor `events` (AM-403) blokuje teraz także komendy.
- Po `respawn`, gdy agent skończy turę, zanim listing pokaże `WORKING`, nakładka pokazuje `WORKING` aż do wygaśnięcia TTL (listing dalej ma starą fazę `from`). Sprawdzić w AM-904.
- `respawn` sesji `Done`/`Failed` zależy od tego, czy CLI na to pozwala (FR-S4 to zakłada). Błąd wraca jako `Runtime(COMMAND_FAILED)`.
- Rozmiar: około 340 linii produkcyjnych (komendy ~150, nakładka ~60, `SessionsState` +35, mapowania ~30, fabryka ~40, `SessionsApi` ~15, pętla ±10), poniżej ENG-C10. Gdyby przekroczyło: osobny PR z `CommandOverlay` i `refresh`.

Uwagi dla kolejnych zadań: AM-305 woła `sessions.commands.stopAllIn` i podmienia `projects:ui`. `app` przekazuje scope z `SupervisorJob` (AM-403).
