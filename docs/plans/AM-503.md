# AM-503 · terminal:ui: karty per projekt, panele, maksymalizacja

Issue: #33 · Wymagania: FR-T2 · ENG-M4, ENG-I1–I8, ENG-C8 · docs/05 (środek: panel terminala), docs/06, docs/11 §2–3 · ADR 0011, ADR 0012 (warunki 2 i 3) · Zależy: AM-502

## Zakres

Decyzje człowieka: zadanie bez podziału; „maksymalizacja” = jeden panel na cały obszar terminala (pozostałe ukryte, ten sam skrót przywraca układ); karty `logs` poza zakresem.

1. Nowy moduł `feature:terminal:ui`: kontroler `TerminalController`, czyste reduktory kart (`TerminalTabs`) i paneli (`PaneLayout`), widok `TerminalArea` (pasek kart pogrupowanych nazwą projektu, panele ze `SwingPanel`, ramka aktywnego panelu, pasek błędu) i `TerminalKeyDispatcher` (ADR 0012, warunek 3).
2. **Karty:** `Shell` (etykieta = nazwa powłoki, np. `zsh`) i `Command` (etykieta od wołającego; użyje jej AM-505 dla `attach · <sesja>`). Zakończony proces: karta zostaje z ekranem i znacznikiem `exit N`. Zamykanie: × na karcie, komenda „Zamknij kartę terminala”.
3. **Panele:** ⌘D dzieli aktywny panel na dwa obok siebie, ⌘⇧D na dwa jeden pod drugim. W nowym panelu startuje powłoka w projekcie aktywnej karty. ⌘⌥→ / ⌘⌥← przełącza na następny / poprzedni panel, ⌘⇧↵ maksymalizuje aktywny panel i przywraca układ. Najwyżej 4 panele, podział 50/50 bez przeciągania (R2 z ADR 0012).
4. **`app`:**
   - `compose.interop.blending=true` w `main` przed `application {}` (warunek 2);
   - `terminalModule(…, LoginShellProcessRunner.defaultShell())`;
   - `terminal.close()` w `onCloseRequest` i w shutdown hooku;
   - `TerminalArea` pod `MissionControl` (gdy są karty albo błąd; 320 dp);
   - menu „Terminal” i komendy palety (grupa `APP`);
   - most klawiszy ⌘ z terminala do skrótów aplikacji;
   - **usunięcie** zbioru `terminalSpike`.

**Nie robimy:** kart `logs` (osobne zadanie: `logsCommand` w `agent-runtime:api`, tryb tylko do odczytu w `terminal:api`), trybu terminala na całe okno, otwierania attach i kropki stanu (AM-505), skrótu `s`, ⌘W, przeciągania kart i granic, katalogu worktree dla nowego panelu, szukania, ustawień i kolorów ze schematu (AM-504/AM-8xx), broadcastu, zapamiętywania układu.

## Zmiany API

Brak zmian w żadnym `api`. Publiczne typy `terminal:ui` (dla `app`, później AM-505/506):

```kotlin
/** The project a tab belongs to; tabs are grouped by [id] and labelled with [name]. [dir]: where shells start. */
public data class TerminalProject(val id: ProjectId, val name: String, val dir: Path)
/** How [TerminalController.split] places the new pane: ⌘D [SIDE_BY_SIDE], ⌘⇧D [STACKED]. */
public enum class SplitAxis { SIDE_BY_SIDE, STACKED }
/** A key press seen while a terminal has the focus; [keyCode] is a `java.awt.event.KeyEvent.VK_*` code. */
public data class TerminalKey(val keyCode: Int, val meta: Boolean, val shift: Boolean, val alt: Boolean, val ctrl: Boolean)
/** What the terminal can do now; `app` enables menu items and palette commands from it. */
public data class TerminalMenuState(
    val hasTabs: Boolean, val canSplit: Boolean, val canSwitchPane: Boolean, val maximized: Boolean,
)

/**
 * Tabs and panes of embedded terminals grouped by project (FR-T2). Opens sessions through [terminals] in [scope]
 * (the window scope, Main dispatcher; not thread-safe). [shellLabel] names shell tabs, e.g. `zsh`. Logs tab and
 * pane ids, kinds and fixed failure categories only, never commands, paths or project names (ENG-C8).
 */
public class TerminalController(terminals: TerminalApi, scope: CoroutineScope, logger: Logger, shellLabel: String) {
    public val menu: StateFlow<TerminalMenuState>
    /** Opens a login shell in [project]'s dir as a new tab shown in the active pane. Failures show in the panel. */
    public fun openShell(project: TerminalProject)
    /** Runs [command] (e.g. `attachCommand`) in a new tab labelled [label], shown in the active pane (AM-505). */
    public fun openCommand(project: TerminalProject, label: String, command: ShellCommand)
    /** Closes the tab of the active pane and its session. */
    public fun closeActive()
    /** Opens a shell of the active tab's project in a new pane next to the active one; ignored unless canSplit. */
    public fun split(axis: SplitAxis)
    /** Activates the next / previous pane in reading order, cyclic. */
    public fun focusNext(); public fun focusPrevious()
    /** Shows only the active pane, or brings the layout back. Ignored with one pane. */
    public fun toggleMaximized()
}

/** The tab bar and the panes; [onAppKey] gets ⌘ keys pressed in a terminal that are not terminal shortcuts. */
@Composable public fun TerminalArea(controller: TerminalController, onAppKey: (TerminalKey) -> Boolean, modifier: Modifier = Modifier)
```

### Decyzje

1. **Grupowanie:** grupy w kolejności pierwszego otwarcia karty projektu, karty w grupie w kolejności otwarcia. Nazwa grupy pochodzi z pierwszej karty.
2. **Karta a panel:** każdy liść pokazuje dokładnie jedną kartę, karta jest w co najwyżej jednym liściu (jeden `JComponent` ma jednego rodzica). Pozostałe karty są ukryte i żyją dalej (R3). Wybór karty z liścia aktywuje ten liść. Wybór karty ukrytej pokazuje ją w aktywnym liściu.
3. **Zamknięcie pokazanej karty:** przy więcej niż jednym liściu liść znika (rodzeństwo zajmuje miejsce `Split`), a aktywny staje się sąsiad w kolejności czytania. Przy jednym liściu pokazuje się ukryta karta: najpierw sąsiad w grupie, potem ostatnia karta innej grupy, a gdy kart nie ma, `layout = null`.
4. **Podział:** kontroler sprawdza `canSplit` (są karty, liści < 4, brak trwającego podziału), potem otwiera powłokę. `SplitOpened` dzieli liść aktywny **w chwili wyniku**. Gdy wtedy jest już 4 liście, karta trafia do aktywnego liścia jak `Opened`. Podział wyłącza maksymalizację.
5. **Maksymalizacja:** wymaga co najmniej 2 liści. Rysowany jest tylko liść aktywny; komponenty pozostałych są odpięte, ale żywe. Zmiana aktywnego liścia (wybór karty, ⌘⌥←/→) przy maksymalizacji pokazuje nowy aktywny. Zejście do 1 liścia zeruje `maximized`.
6. **Fokus:** zmiana `active` → `requestFocusInWindow()` na komponencie karty. Klik myszą w panel zmienia właściciela fokusu: słuchacz `focusOwner` w `KeyboardFocusManager` mapuje komponent na liść i wysyła `FocusPane`. Zdarzenie jest idempotentne, więc nie powstaje pętla.
7. **Błędy otwarcia:** `WorkDirMissing`/`StartFailed` → pasek błędu (z ×) i WARN `terminal tab open failed` (`reason`). `Closed` (zamykanie aplikacji) jest ignorowane. Kontroler zbiera `exitCode` każdej karty; job jest anulowany przy zamknięciu karty.
8. **Klawisze:** `TerminalKeyDispatcher` (AWT) działa tylko, gdy właściciel fokusu leży w komponencie karty (`SwingUtilities.isDescendingFrom`; `focusOwner` wstrzykiwany w testach). Zdarzenia `KEY_PRESSED` z ⌘ trafiają najpierw do `TerminalShortcuts.commandOf(key)`: ⌘D, ⌘⇧D, ⌘⌥←, ⌘⌥→, ⌘⇧↵. Dopiero bez trafienia idą do `onAppKey`; `false` zostawia klawisz JediTermowi (⌘C, ⌘V, ⌘↑/↓). Bez ⌘ dispatcher nic nie przechwytuje.
9. **Most w `app` (`TerminalKeys`):** czysta funkcja `chordOf(TerminalKey): KeyChord?`, potem ⌘K → `palette.open()`. Każdy inny akord to jednoakordowa komenda rejestru z `META` uruchamiana w zakresie okna. Gdy fokus nie jest w terminalu, ⌘D, ⌘⇧D i ⌘⇧↵ obsługuje menu „Terminal” (`ChordKey` je wyraża), a ⌘⌥←/→ menu przez `KeyShortcut` Compose (brak `LEFT/RIGHT` w `ChordKey`; `command-palette:api` bez zmian, w palecie bez etykiety skrótu).
10. **Komendy palety (grupa `APP`):**
    - „Nowa karta powłoki” (⌘T): dla projektu wybranego w sidebarze, bez otwartego dialogu;
    - „Podziel panel obok” / „pod spodem”: przy `canSplit`;
    - „Następny / poprzedni panel”: przy `canSwitchPane`;
    - „Maksymalizuj panel” / „Przywróć panele”: zależnie od `maximized`;
    - „Zamknij kartę terminala”: przy `hasTabs`.

    Przycisk „+” na końcu grupy otwiera powłokę w projekcie tej grupy.
11. **Testowalność:** `TerminalArea` ma wewnętrzny parametr `paneContent: @Composable (JComponent) -> Unit` (domyślnie `SwingPanel`). Testy UI podstawiają znacznik z `testTag`.

### Odchylenia od planu (implementacja)

- `paneContent` jest publicznym, nullowalnym parametrem `TerminalArea` (`null` = `SwingPanel`), a nie wewnętrznym: `app` jest osobnym modułem i przekazuje go w testach. `AgentManagerApp` dostaje jeden slot `terminalPanel: (@Composable (Modifier) -> Unit)?` (ENG-C2, max 5 parametrów); `TerminalArea` nic nie rysuje bez kart i bez błędu.
- `@Suppress("TooManyFunctions")` na `TerminalController`: 11 operacji (`openShell`, `openCommand`, `closeActive`, `split`, `focusNext`, `focusPrevious`, `toggleMaximized`, `select`, `close`, `focusPane`, `dismissError`) wymagają testy i widok, a detekt zgłasza klasę od 11 funkcji; logika jest w reduktorach, więc rozbicie klasy tylko by to ukryło.
- Zdarzenia reduktora mają pod-interfejsy `OfTab`/`OfPane` (złożoność `reduce` ≤ 10); `WindowControllers.kt` w `app` (LongMethod `MainWindow`); skróty terminala w `AppShortcuts`.
- Most ⌘ nie przepuszcza ⌘⌫, ⌘↑, ⌘↓ (edycja tekstu; ⌘⌫ usuwa projekt). Komendy terminala są ukryte też przy otwartym dialogu Mission Control.
- Ręczna lista kontrolna, dodatkowo: fokus po zamknięciu ostatniej karty, `KEY_TYPED` z ⌘ w terminalu, podwójna obsługa skrótu (dispatcher i natywne menu).

## Ryzyka i pytania

**Pytania blokujące:** brak (podział i maksymalizację rozstrzygnął człowiek).

- **Szacunek** (linie netto `src/main` i Gradle, +30% wg Lekcji):
  - `terminal:ui`: typy i karty 60, panele 75, stan 25, kontroler 120, widok (pasek, panele, błąd) 160, fokus i dispatcher 55, skróty 20, napisy, tagi i Gradle 30;
  - `app`: Main 12, wiring okna 25, menu 40, komendy 55, most ⌘ 30, Gradle 5;
  - razem ~710, **ok. 920 z zapasem**, usunięte ~210 (spike).

  Duży PR z decyzji człowieka; przegląd ułatwiają commity 1–9. Composable blisko LongMethod mają od razu osobne funkcje (`TabGroupChip`, `TabChip`, `PaneFrame`, `ErrorBar`, `SplitPanes`).
- **Podwójny skrót:** dispatcher konsumuje ⌘ z terminala, a natywny `MenuBar` macOS może obsłużyć ten sam akcelerator. Sprawdzić ręcznie. W razie podwójnego wywołania dispatcher przepuszcza akordy obecne w menu i przechwytuje tylko ⌘K oraz ⌘⌥←/→.
- **Przepinanie komponentów JediTerm** między `SwingPanel` (wybór karty, podział, maksymalizacja) nie było sprawdzone w spike'u (R3 dotyczył jednej karty). Ręczny test z `top`. Jeśli widżet się psuje, rozwiązanie zostaje w `terminal:ui` (np. stały `SwingPanel` per karta ukrywany rozmiarem 0).
- Blending (F6) musi być ustawiony przed pierwszym `application {}`. Artefakty szybkiego resize (R2) są tylko do obserwacji.
- Kover nie ma progu dla `ui`. Reduktory i kontroler mają pełne testy jednostkowe, natomiast `SwingPanel` i słuchacz fokusu są sprawdzane tylko ręcznie.
