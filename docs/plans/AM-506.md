# AM-506 · Skrót r: attach wybranej sesji w karcie terminala z fokusem na odpowiedzi

Issue: #96 · Wymagania: FR-K2 (część: `r`), FR-K1, FR-T1 · ENG-I1, ENG-I2, ENG-C2, ENG-C8 · docs/05 „Skróty klawiszowe” (`r` Odpowiedz wybranej sesji) · ADR 0013 (przyjęta, wariant „Etapami”), ADR 0011 · Zależy: AM-503, AM-505, AM-411 (scalone)

## Zakres

ADR 0013 ustala, że w MVP `r` otwiera `claude attach <id>` w karcie terminala, a użytkownik odpowiada w pełnym TUI (pytanie tekstowe, opcje, zgoda). Nic nie wpisujemy do PTY, bo to zakres spike'u AM-507. Całą drogę daje AM-505: `attachTarget()` → `SessionAttacher` → `TerminalController.openCommand`, a `FocusActivePane` daje fokus widżetowi nowej karty. Zadanie nie zmienia `api` żadnego feature ani `terminal:ui`.

**Czym `r` różni się od ⏎:** `r` działa tylko dla sesji, która czeka na użytkownika (`SessionState.isWaiting`: `AwaitingInput` albo `AwaitingPermission`). Reszta jest taka sama jak przy ⏎.

1. **`mission-control:ui`**: `AttachTarget` dostaje pole `waiting`, a `SessionActionsState` flagę `canReply`. W kontrolerze nie dochodzi żadna funkcja, bo `attachTarget()` zwraca już `waiting`.
2. **`app`**: komenda palety „Odpowiedz w terminalu” ze skrótem `r` (`AppShortcuts.REPLY_SESSION`). Uruchamia ją `SessionAttacher.replySelected()`. Komendę oferuje ten sam `AttachCommands`.

**Nie robimy:** wpisywania odpowiedzi ani pola odpowiedzi (AM-507, FR-S5), fokusu istniejącej karty sesji i kropki stanu (AM-510, #109), przycisków „Attach” i „Odpowiedz” w panelu szczegółów (pytanie 1), pozycji w menu okna.

## Zmiany API

`sessions:api`, `agent-runtime:api`, `terminal:*`, `command-palette:*`, `projects:*`: brak. Publiczne API `mission-control:ui` (woła je tylko `app`). Nowe pola są na końcu i mają wartość domyślną, więc istniejące wywołania się nie zmieniają.

```kotlin
/**
 * The selected session to attach to: `⏎` (AM-505) and `r` (AM-506, only when [waiting]). [session] id, display [name]
 * for the tab label and the registered [project] whose tab group gets the tab. [name] and [project] are user data:
 * log [session] only (ENG-C8).
 * @property waiting the session waits for the user ([SessionState.isWaiting]): a question or a permission request.
 */
public data class AttachTarget(val session: SessionId, val name: String, val project: Project, val waiting: Boolean = false)

// SessionActionsState
/** @property canReply [canAttach] and the session waits for the user (`r`, ADR 0013); also while an action runs. */
val canReply: Boolean = false
```

Wewnętrzne: `SessionAttach.targetOf` ustawia `waiting = session.state.isWaiting`. W `actionsOf` jest `val attach = SessionAttach.targetOf(...)`, a z niego `canAttach = attach != null` i `canReply = attach?.waiting == true`. KDoc `attachTarget()` dostaje zdanie: „`⏎` and `r` (when [AttachTarget.waiting])”.

`app`:

```kotlin
internal val REPLY_SESSION: Shortcut = Shortcut.of(chord('r'))   // AppShortcuts
/** Attach (`⏎`) and reply (`r`) commands of the palette; each by its flag, none while a dialog is open. */
internal fun attachCommands(dialogOpen: Boolean, actions: SessionActionsState, attach: () -> Unit, reply: () -> Unit): List<Command>
// SessionAttacher
/** Like [attachSelected], but only for a target that is [AttachTarget.waiting]; no-op otherwise. */
fun replySelected()
```

`attachSelected` i `replySelected` dzielą prywatne `open(target, event)`. Budowę obu `Command` robi prywatny pomocnik z najwyżej 5 parametrami. `attachCommands` ma 2 `return` (limit ReturnCount): wczesny `emptyList()` i `listOfNotNull(...)`.

### Decyzje

1. **Kiedy `r` działa** (tabela 1): jak ⏎ (zaznaczona widoczna sesja zarejestrowanego projektu, brak dialogu MC, dozwolone przy otwartym podglądzie i działającej akcji), ale tylko gdy `waiting`. Należą tu oba stany, bo ADR 0013 kieruje do TUI także zgody.
2. **Sesja nie czeka, nic nie zaznaczono, sesja bez projektu, otwarty dialog** (MC albo projektów): komendy nie ma, `r` nic nie robi i nie jest zużyty (`onChord` → `false`). Nie pokazujemy komunikatu, tak samo jak przy ⏎. Do zwykłego attachu jest ⏎. W widoku globalnym „Czekające” sesja bez projektu też nie dostaje `r`, bo karta wymaga grupy projektu.
3. **Cel czytany na świeżo** (lekcja o `stateIn`): `replySelected` czyta `attachTarget()` i sprawdza `waiting` w chwili wykonania. Komenda oferowana na podstawie spóźnionego `canReply` nie otworzy więc karty sesji, która właśnie przestała czekać. Ten strażnik ma test jednostkowy, który padnie po usunięciu warunku.
4. **„Fokus na odpowiedzi”** to fokus klawiatury w widżecie nowej karty (`FocusActivePane`, AM-505). TUI `claude attach` pokazuje pytanie albo prośbę o zgodę na dole, a pole odpowiedzi ma kursor. Nic nie wpisujemy i nie przewijamy (ADR 0013, AM-507). Kolejne klawisze, także `r`, idą do PTY, bo `TerminalKeys` mostkuje tylko akordy z ⌘.
5. **Karta**: zawsze nowa, z tą samą etykietą `attach · <nazwa>` (`terminal.attachTab`) i tą samą komendą co ⏎. AM-510 rozpozna wtedy kartę sesji bez względu na to, czy otwarto ją przez `r` czy ⏎. Fokus istniejącej karty należy do AM-510; ADR 0013 go nie wymaga.
6. **Droga klawisza `r`**: tak jak `j`/`k`/`x` przez `Window.onKeyEvent` → `palette.onKeyEvent`. Pole szukania i paleta zjadają litery, dialogi (`Popup(focusable = true)`) dają pustą listę komend. Przyciski i wiersze MC są już niefokusowalne (AM-505), więc nie dochodzi nowy fokusowalny element.
7. **Komenda**: id `sessions.reply`, tytuł `command.replySession=Odpowiedz w terminalu`, `keywords = [reply, odpowiedz, answer, zgoda]`, grupa `SESSION`, skrót `r` (bez ⌘).
8. **Logi**: INFO `session reply` z `sessionId`, bez nazwy i ścieżki. Brak celu i sesja, która nie czeka, nie są logowane.

## Ryzyka i pytania

**Pytania blokujące: brak.** Pytania nieblokujące (zostaje domyślna decyzja, jeśli człowiek nie zdecyduje inaczej):

1. **Przyciski „Attach” i „Odpowiedz” w panelu szczegółów** (docs/05; pytanie 3 z AM-505): domyślnie **poza zakresem**, do nowego wpisu w roadmapie (`mission-control:ui`, `app`) po AM-507. Powody: (a) FR-K2 dotyczy tylko klawiatury; (b) według ADR 0013 „Odpowiedz” w panelu zamieni się po dobrym wyniku AM-507 w pole szybkiej odpowiedzi, więc przycisk zrobiony teraz trzeba by przerobić; (c) klik musi dojść do `app` przez nowy publiczny kanał (callback w `MissionControl(...)` albo strumień żądań z kontrolera). `SessionPage` ma już 8 parametrów, a `MissionControlController` 10 funkcji, więc to osobna decyzja projektowa i dodatkowe ok. 60 linii z testami UI.
2. **`r` na sesji, która nie czeka**: domyślnie nic się nie dzieje (decyzja 2). Inna możliwość to działanie jak ⏎ albo krótki komunikat „Sesja nie czeka na odpowiedź”. Komunikat wymaga nowego stanu UI, a działanie jak ⏎ zaciera różnicę między `r` a ⏎.
3. **Etykieta karty**: domyślnie `attach · <nazwa>` (decyzja 5). Osobna etykieta `odpowiedź · <nazwa>` utrudniłaby AM-510.

**Rozmiar:** netto w `src/main` (bez importów, KDoc i pustych linii): `mission-control:ui` ok. 6 (pole, `targetOf`, `actionsOf`), `app` ok. 30 (`attachCommands` z pomocnikiem 15, `replySelected`/`open` 8, skrót, `AttachCommands`, teksty 7). Razem ok. 36, z zapasem 30% **ok. 50**. Testy ok. 250 linii.

**Ryzyka:**

- Lekcja o KDoc z wyliczeniami: poprawić teksty, które mówią tylko o ⏎ albo attach. Dotyczy to KDoc `AttachTarget`, `SessionAttach` („When `⏎` can attach”), `attachTarget()` („The session `⏎` attaches to”), `actions` (dopisać `canReply`), `SessionActionsState`, `attachCommands` („The attach command…”), `SessionAttacher`, `AttachCommands` oraz komentarza klasy `AttachWindowTest`, jeśli wylicza skróty.
- Lekcja o `stateIn`: dostępność komendy wynika z `canReply` po `stateIn`, więc przy pierwszym zaznaczeniu może się spóźnić o klatkę, tak jak ⏎. Opisać to w KDoc `AttachCommands`.
- `MissionControlController` zostaje przy 10 funkcjach (limit TooManyFunctions to 11), bo nie dodajemy `replyTarget()`. Implementer nie może dodać nowej funkcji „dla wygody”.
- `SessionState.isWaiting` pochodzi z `sessions:api`. Jeśli `RuntimeMapping` mapuje nieznane `WaitingFor.Other` na `AwaitingInput`, `r` otworzy attach także w takim przypadku. To akceptowalne, bo pełne TUI obsłuży każdy rodzaj oczekiwania.
- Ręcznie: czy przy szybkim `r`, `r` dwa klienty attach jednej sesji nie psują TUI (to samo ryzyko i ta sama decyzja co w AM-505).
