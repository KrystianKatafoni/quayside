# AM-601 · KtorHookServer (127.0.0.1, token z Keychain)

Issue: #4 · Wymagania: NFR-4, ENG-C8, ENG-I1, ENG-T2 · docs/11 §4 (`AgentEventSource`), §6, ADR 0004, ADR 0017 · Etap: M6 · Zależy: AM-203

## Zakres

Serwer HTTP w `agent-runtime:impl`, który przyjmuje hooki Claude Code (`Notification`, `Stop`, `StopFailure`, `SessionEnd`; `SessionStart` jest przyjmowany i pomijany), sprawdza token i publikuje `AgentEvent` przez `AgentEventSource`. Token trzyma Keychain.

Dlaczego to zadanie, a nie AM-701: AM-701 zależy od AM-603, a to od AM-601 i AM-403; AM-601 jest pierwszym wpisem roadmapy, którego zależności są scalone, i jest początkiem ścieżki AM-601 → AM-603 → AM-701 → AM-509.

Nie robimy: `HookInstaller` (AM-602), scalania z pollingiem (AM-603), podpinania w `app` (konsumenta jeszcze nie ma; AM-603 podepnie fabrykę w composition root), obsługi `SessionStart` jako zdarzenia (brak wariantu w `api`), zmian w `api`.

## Moduły

- `feature:agent-runtime:impl`: `HookPayloadParser` (czysty), `HookToken` + `KeychainHookTokenStore`, `KtorHookServer`, fabryka `hookEventSourceModule` i testy.
- `gradle/libs.versions.toml`: Ktor 3.5.2.
- `docs/adr/0017-…`, `docs/compat.md`, `CHANGELOG.md`, `docs/ROADMAP.md` (`[~]`).
- `feature:agent-runtime:api`: **bez zmian**. `AgentEventSourceContract` z `testFixtures` działa teraz także na prawdziwym serwerze.

## Zmiany API

Brak w `api`. W `impl` jedyna publiczna nowość to fabryka:

```kotlin
public fun hookEventSourceModule(
    process: ProcessRunner, clock: Clock, logger: Logger, scope: CoroutineScope, homeDir: Path, port: Int = 47321,
): AgentEventSource
```

Mapowanie hooków (pola z docs/03; nieznane pola są ignorowane):

| Hook | Warunek | Zdarzenie |
| --- | --- | --- |
| `Notification` | `notification_type` = `agent_needs_input`, `idle_prompt`, `elicitation_dialog` | `NeedsInput(question = message)` |
| `Notification` | `notification_type` = `permission_prompt` | `PermissionRequested(tool)`; `tool` z `message` (`… permission to use <Tool>`), inaczej `null` |
| `Stop` | — | `TurnEnded(last_assistant_message)` |
| `StopFailure` | — | `Failed(error_type`, a w razie braku `error`; inaczej `unknown`) |
| `SessionEnd` | — | `SessionEnded(reason, inaczej unknown)` |
| inne | — | 200, bez zdarzenia |

`session_id`, `cwd`, `hook_event_name` są wymagane (inaczej 400). `kind` i `reason` przechodzą tylko jako krótkie tokeny (`[A-Za-z0-9_.:-]{1,40}`), inaczej `unknown`.

## Ryzyka i pytania

- Nazwy pól `StopFailure` (`error_type` vs `error`) i `Notification` nie są zweryfikowane nagraniem prawdziwego hooka; parser toleruje oba warianty, a po AM-602 trzeba nagrać prawdziwe payloady do `docs/compat.md`.
- `security add-generic-password -w <token>` pokazuje token w argumentach procesu na chwilę (ADR 0017, pkt 3).
- Testy portu i pętli zwrotnej używają prawdziwych gniazd; test „brak nasłuchu poza pętlą zwrotną” jest pomijany, gdy maszyna nie ma innego adresu IPv4.
- Lokalny Gradle w chmurze bywa blokowany przez HTTP 429 z Maven Central; weryfikacją jest CI w PR.
