# AM-610 · Ostrzeżenie przy usuwaniu projektu z hookami Quayside

Issue: #109 · Wymagania: FR-P3, FR-P4, NFR-5, ENG-C2, ENG-C8 · docs/11 §3 · Zależy: AM-609 (plan `AM-609.md`, „Pytania” 3)

## Zakres

Dialog usuwania projektu (FR-P3, `projects:ui`) przed pokazaniem pyta `app` o hooki Quayside w `<dir>/.claude/settings.local.json` (`HookInstaller.status(HookScope.Project(dir))`). Gdy są (`Installed` albo `Partial`), dialog mówi, że po usunięciu z listy hooki zostaną w pliku i znikną z okna „Hooki Claude Code”, i daje przycisk „Odinstaluj hooki”. Ten przycisk usuwa tylko nasze hooki (tak jak „Odinstaluj” w oknie hooków, `backup = null`). Dialog zostaje otwarty z nowym statusem i komunikatem, a wybór usunięcia (FR-P4: „Usuń” albo „Zatrzymaj sesje i usuń” / „Usuń z listy, sesje działają dalej”) działa bez zmian.

Nie robimy: zmian w `projects:api` ani w `agent-runtime` (`api`, `impl`); hooków w `.claude/settings.json` projektu (AM-609 instaluje tylko w `settings.local.json`); przycisku łączącego odinstalowanie i usunięcie (patrz „Pytania” 2); przywracania kopii; zmian w oknie hooków.

## Zmiany API

Brak zmian w żadnym module `api`. Nowe publiczne typy `projects:ui` (widzi je tylko `app`, jak `DirectoryPicker`):

```kotlin
/**
 * Quayside hooks in a project's `.claude/settings.local.json`, supplied by `app` (AM-610). The remove dialog
 * reads them to warn that removing the project from the list leaves them in the file (FR-P3).
 * Both functions may be called from any dispatcher, never block the calling thread and never throw except
 * cancellation. They never create [dir] or its `.claude` folder.
 */
public interface ProjectHooks {
    /** Our hooks in the local settings of [dir]; [ProjectHooksState.ABSENT] when [dir] is not a directory. */
    public suspend fun status(dir: Path): ProjectHooksState

    /** Removes only our hooks from the local settings of [dir]; other settings stay. Never restores a backup. */
    public suspend fun uninstall(dir: Path): Outcome<Unit, ProjectHooksError>
}

/** What the remove dialog shows about the hooks of a project. */
public enum class ProjectHooksState {
    /** No hooks of ours, no file, or the project folder is gone: nothing to warn about. */
    ABSENT,
    /** All or some of our hooks are in the file: warn and offer "Odinstaluj hooki". */
    PRESENT,
    /** The file could not be read: say so, offer nothing. */
    UNKNOWN,
}

/** Why [ProjectHooks.uninstall] failed; a fixed category, never a path or file content (ENG-C8). */
public enum class ProjectHooksError { UNREADABLE, WRITE_FAILED }

/** What `app` supplies to [ProjectsController] besides the `api` modules: keeps the constructor at 6 (ENG-C2). */
public class ProjectsPorts(public val picker: DirectoryPicker, public val hooks: ProjectHooks)

// Changed constructor (picker → ports, still 6 parameters):
public class ProjectsController(projects: ProjectsApi, inspector: ProjectInspector, sessions: SessionsApi,
    ports: ProjectsPorts, scope: CoroutineScope, logger: Logger)
```

Typy wewnętrzne:

```kotlin
// projects:ui
data class ConfirmRemove(val project: Project, val active: SessionCounts?,

//   (notice text: "uninstalled" or the failure category; logs only projectId and the category)

// app

internal class InstallerProjectHooks(installer: HookInstaller, io: CoroutineDispatcher,
    isDirectory: (Path) -> Boolean = Files::isDirectory) : ProjectHooks
internal class HookDeps(installer, backupDir, offer, targets, val projectHooks: ProjectHooks)
```

## Reguły

1. **Otwarcie.** `RemoveSelectedRequested` → `begin(Waiting.CHECKING_HOOKS)` → `hooks.status(project.dir)` → `ensureActive()` → `ConfirmRemove` z `confirmRemove(project)` (liczby sesji z chwili odczytu, jak dziś) i `hooks`. „Anuluj”/Esc w trakcie odczytu anuluje go; wynik po anulowaniu nie otwiera dialogu.
2. **Odinstalowanie.** `UninstallHooks` działa tylko przy `ConfirmRemove` z `hooks == PRESENT` (strażnik w kontrolerze, nie tylko brak przycisku). `begin(BUSY)` → `uninstall` → ponowny odczyt statusu (także po błędzie: plik mógł się zmienić) → ten sam `ConfirmRemove` (`active` bez zmian) z nowym `hooks` i `hooksNotice`. Projekt zostaje na liście; nic nie jest usuwane automatycznie.
3. **Zgoda (NFR-5).** Plik zmienia tylko klik „Odinstaluj hooki”. Fokus startowy w każdym `ConfirmRemove` ma „Anuluj” (także po powrocie z `BUSY`), więc Space i Enter nie uruchamiają ani odinstalowania, ani usunięcia. Wskaźnik fokusu `AmButton` musi być widoczny.
4. **Projekt bez folderu** (AM-609): adapter zwraca `ABSENT` bez wołania instalatora; `uninstall` zwraca `Err(WRITE_FAILED)` bez wołania instalatora (`SettingsFiles.write` odtworzyłby folder).
5. **Mapowanie w `app`.** `NotInstalled` → `ABSENT`; `Installed`, `Partial` → `PRESENT`; `Unreadable` → `UNKNOWN`. `SettingsUnreadable` → `UNREADABLE`; `WriteFailed`, `BackupNotFound` (niemożliwe przy `backup = null`) → `WRITE_FAILED`.
6. **Teksty** bez ścieżek i nazw (nagłówek `projects.properties`): `remove.checkingHooks`, `remove.hooks.present` (hooki w `.claude/settings.local.json` zostaną po usunięciu z listy i nie będzie ich w oknie „Hooki Claude Code”), `remove.hooks.unknown`, `remove.hooks.uninstall`, `remove.hooks.uninstalled`, `remove.hooks.failed.unreadable`, `remove.hooks.failed.writeFailed`.
7. **Logi.** `projects:ui`: „project hooks uninstall failed” z `projectId` i kategorią; `app` nie loguje. Przy sukcesie `info` „project hooks uninstalled” z samym `projectId`. Nigdy ścieżka ani nazwa (ENG-C8).
8. **ENG-C2.** Konstruktor kontrolera 6, `ProjectCommands` 4, `HookDeps` 5 pól. `ConfirmRemove` i nowe composable ≤ 30 linii treści (zmierzyć ręcznie); przy TooManyFunctions w kontrolerze logika IO idzie do `ProjectCommands`. **Odstępstwo od planu:** by zmieścić się w progu (11 funkcji), `fail` wchłonięty został w `pickAndInspect`, a odczyt hooków przed dialogiem jest lambdą w `onIntent`; kontroler ma 11 funkcji, czyli leży na progu TooManyFunctions. Fokus startowy ustawia `LaunchedEffect(hooks, hooksNotice)`: kliknięty „Odinstaluj hooki” trzyma fokus i znika z dialogu.

## Ryzyka i pytania

Pytania blokujące: brak (żadne `api` się nie zmienia, bez nowego formatu pliku i bez ADR; moduły zgodne z roadmapą).

Pytania niezablokowane (plan przyjmuje rekomendację; lead może zmienić przed startem):

1. **Skąd dialog bierze status.** Dokument 11 §3 reguła 1 pozwala `ui` → `api` dowolnego feature, więc `projects:ui` mógłby dostać `HookInstaller` z `agent-runtime:api`. Warianty: (A) wąski port `ProjectHooks` w `projects:ui`, adapter w `app` — **rekomendacja**: mały interfejs (ENG-I2), dialog nie może instalować, sprawdzenie folderu zostaje w `app` obok AM-609; (B) zależność `projects:ui` → `agent-runtime:api` i `HookInstaller` w kontrolerze — mniej kodu w `app`, ale nowa krawędź w grafie, mapowanie `HookError` i IO folderu w `ui`; (C) `ProjectInspector.inspect(dir).hooks` — odpada: łączy `settings.json` i `settings.local.json`, a odinstalowanie i tak wymaga portu.
2. **Kształt akcji.** (A) „Odinstaluj hooki” jako osobny krok, dialog zostaje — **rekomendacja**: jedna akcja na przycisk, przyciski FR-P4 bez zmian; (B) „Odinstaluj i usuń” — przy działających sesjach daje 4 przyciski zapisujące (2×2) i dwa skutki jednym klikiem.
3. Odczyt przed dialogiem (`CHECKING_HOOKS`) zamiast dialogu z przyciskami czynnymi w trakcie odczytu: użytkownik nie usunie projektu, zanim zobaczy ostrzeżenie. Koszt: krótki panel „Sprawdzanie…”.
4. Fokus startowy na „Anuluj” obejmuje też dialog bez hooków (dziś brak fokusu startowego); jedna reguła zamiast warunku.

Ryzyka:

- Zmiana konstruktora `ProjectsController` dotyka 4 miejsc w testach `app` i `ControllerWorld`; istniejące testy usuwania potrzebują przejścia przez `CHECKING_HOOKS` (fake zwraca od razu, `runCurrent`).
- Odinstalowanie przy działających sesjach: Claude Code może trzymać hooki wczytane przy starcie sesji, więc zdarzenia mogą dalej przychodzić do końca sesji. Nieszkodliwe; nie obiecujemy w tekście natychmiastowego skutku.
- Okno hooków i dialog usuwania nie są otwarte naraz (`dialogOpen` ukrywa komendę hooków); równoległe operacje i tak serializuje mutex instalatora.
