# AM-704 · Ekran ustawień powiadomień

Issue: #12 · Wymagania: FR-N1–FR-N4, NFR-6, NFR-10 · docs/07, docs/11 §4, ENG-I1–I8, ENG-C2, ENG-C8, ENG-C10 · Zależy: AM-702, AM-703 (scalone) · Wzór: AM-508 część B

## Zakres

Dialog „Ustawienia powiadomień” nad oknem (jak `TerminalSettingsDialog`: `Popup` na całe okno, Escape = Anuluj, Tab po kontrolkach, przewijanie w pionie), otwierany z palety (`notifications.settings`) i z menu „Widok”. Zmienia `NotificationSettings` przez `NotificationSettingsRepo.update`; nowe wartości działają od razu (centrum czyta ustawienia przy każdym zdarzeniu).

**Podział na dwie części (dwa PR do #12, `[x]` w roadmapie dopiero po B).** Szacunek całości to ok. 700 linii netto `src/main` (z zapasem 30%), więc jeden PR łamie ENG-C10 (≤ 400):

- **Część A (`feat/AM-704-notification-settings-screen`): dialog i kanały.** Kontroler, dialog, wspólne kontrolki, sekcja „Zdarzenia i kanały” (macierz 7 rodzajów × 4 kanały), przełączniki globalne „Popupy” i „Głos”, próg N minut dla `RUNNING_LONG`, komenda palety i pozycja menu w `app`. **Ok. 390 linii** (zmierzone po implementacji: netto ok. 596 z importami, ok. 480 bez importów, brutto ok. 715).
- **Część B (`feat/AM-704-popup-voice-settings`): popup i głos.** Sekcja „Popup” (pozycja z 6, czas, maks. naraz, styl), sekcja „Głos” (głos z listy `say -v ?`, tempo, głośność, 7 szablonów z „Przywróć domyślny”, trzy przełączniki), port `VoiceCatalog` w `api` i adapter w `impl`, reguła szablonów w `api`. **Ok. 300 linii.**

Zasady:

- Zapis zaczyna od **bieżących** ustawień (`update { current -> … }`), więc dialog nie nadpisuje pól, których nie pokazuje (AM-705 doda kolejne).
- Macierz i szablony zapisujemy **tylko jako odstępstwa**: rodzaj z kanałami równymi `defaultChannels(kind)` i szablon równy `defaultTemplate(kind)` albo pusty są usuwane z mapy. Dlatego „Przywróć domyślny” to zwykła edycja szkicu (tekst = domyślny), a po zapisie wpis znika z `templates`.
- Liczby (N minut, maks. naraz, tempo, głośność) są w szkicu tekstem (jak AM-508), sprawdzane przy zapisie; `require` w `api` nigdy nie rzuca z dialogu.
- Szablon wpisany w UI z `[[` lub `]]` (komendy osadzone `say`) albo dłuższy niż 200 znaków jest odrzucany przy zapisie z komunikatem pod polem.
- „Wycisz przy aktywnym mikrofonie” jest widoczny i zapisywany, z adnotacją „Jeszcze nie działa: wykrywanie mikrofonu czeka na ADR 0018” (tekst w zasobach; usuwa go zadanie adaptera CoreAudio).
- Lista głosów ładuje się w tle przy pierwszym `open()`; do tego czasu i po błędzie wybór ma tylko „Głos systemowy” i zapisany głos. Zapisany głos spoza listy ma etykietę „(niezainstalowany)”.
- Wszystkie teksty w `i18n/notification-settings.properties` (NFR-10); checkboxy macierzy mają etykiety dostępności „<rodzaj> – <kanał>” (NFR-6).

**Nie robimy:** ciszy nocnej, trybu Skupienia, wyjątków per projekt, języka głosu wg projektu (AM-705), przycisku „Testuj głos” (wymaga portu mowy w `api`, pytanie 3), popupu systemowego macOS i „wszystkich monitorów” (brak modelu; natywny most, docs/07 dopuszcza na MVP tylko własny popup), przełączników akcji w popupie i grupowania (stałe zachowanie), podglądu popupu, wspólnego modułu `core:design-system`.

## Zmiany API

Inne feature: bez zmian. Publiczne API `notifications:ui` (używa go `app`):

```kotlin
// notifications:ui (A; B dodaje pola popup i speech oraz parametr voices)
/** The settings as the dialog edits them (AM-704); numbers stay text until save. [matrix] has every kind. */
public data class NotificationDraft(
    val popups: Boolean, val voice: Boolean,
    val matrix: Map<NotificationKind, Set<NotificationChannel>>,
    val runningLongMinutes: String,
    val popup: PopupDraft,          // B: position, duration, maxVisible: String, style
    val speech: SpeechDraft,        // B: voice: VoiceId?, rate: String, volume: String,
)                                   //    templates: Map<NotificationKind, String> (every kind), 3 switches
public enum class NotificationField { RUNNING_LONG_MINUTES, MAX_VISIBLE, RATE, VOLUME, TEMPLATE }
/** A field the last save refused; [kind] only for [NotificationField.TEMPLATE]. */
public data class InvalidField(val field: NotificationField, val kind: NotificationKind? = null)
/** The open dialog. [voices]: installed voices, null while loading or after a failure ([voicesFailed]). */
public data class NotificationDialogState(
    val draft: NotificationDraft, val invalid: InvalidField?,
    val saveError: NotificationSettingsError?, val voices: List<VoiceOption>?, val voicesFailed: Boolean,
)
/**
 * Logic of the "Ustawienia powiadomień" dialog (FR-N1–N4). Main thread; [save] writes in [scope], one write at a
 * time, a result arriving after cancel is dropped. Logs nothing (templates are the user's).
 */
public class NotificationSettingsController(repo: NotificationSettingsRepo, voices: VoiceCatalog, scope: CoroutineScope) {
    public val state: StateFlow<NotificationDialogState?>
    public fun open()
    public fun edit(change: (NotificationDraft) -> NotificationDraft)
    public fun restoreTemplate(kind: NotificationKind)   // B: text of the draft = defaultTemplate(kind)
    public fun save()
    public fun cancel()
}
@Composable public fun NotificationSettingsDialog(controller: NotificationSettingsController)
```

## Ryzyka i pytania

**Pytania blokujące: brak.** Pytania nieblokujące (plan przyjmuje wariant rekomendowany):

1. **Moduły spoza roadmapy**: roadmapa podaje tylko `notifications:ui`; plan zmienia też własne `notifications:api` i `notifications:impl` (port listy głosów, decyzja z AM-703, pyt. 5) oraz `app` (komenda, menu, spięcie). Bez nich ekranu nie da się otworzyć ani wybrać głosu. Akceptujesz?
2. **Podział A/B** jak w AM-508 (dwa PR do #12, `[x]` po B). Akceptujesz?
3. **„Testuj głos”** z docs/07 (zrzut 21): wymaga portu mowy w `api` (`SpeechPort` jest `internal` w `impl`). Rekomendacja: osobne zadanie po AM-705.
4. **Miejsce w menu**: „Widok → Ustawienia powiadomień…” (bez skrótu). Alternatywa: ⌘, z menu aplikacji, gdy powstanie wspólne okno ustawień.
5. **Szablony z `[[` w pliku** (edycja ręczna `notifications.json`): plan odrzuca je tylko w UI. Czy serializer ma je traktować jak pusty szablon (domyślny)? Rekomendacja: tak, w osobnym małym zadaniu.

**Rozmiar** (netto `src/main`, z zapasem 30%): A — kontroler i szkic ok. 120, dialog i macierz ok. 120, kontrolki ok. 100, teksty i tagi ok. 25, `app` ok. 45 → **ok. 390** (blisko limitu: gdy po kontrolerze i dialogu pomiar przekroczy 340, przenieść przełączniki globalne i próg N do B). B — `api` ok. 25, `impl` ok. 45, sekcje popup i głos ok. 150, kontroler ok. 50, teksty ok. 25, `app` ok. 5 → **ok. 300**.

**Ryzyka:**

- Kopia kontrolek z `terminal:ui` (ok. 100 linii): `ui` nie może zależeć od innego `ui`, a `core:design-system` nie istnieje. Wydzielenie do wspólnego modułu to zmiana granic modułów (ADR) — poza zakresem; dopisać do roadmapy.
- Długi dialog (28 checkboxów, 7 szablonów) wymaga `verticalScroll`; fokus z Tab musi przewijać do pola — sprawdzić testem ekranu i ręcznie.
- Composable blisko LongMethod (30) i ENG-C2 (≤ 5 parametrów): macierz jako pętla po `NotificationKind.entries` × `NotificationChannel.entries`, sekcje w osobnych plikach (TooManyFunctions).
- Format `say -v ?` nie jest dokumentowany; parser pomija wiersze, których nie rozumie, a zapisany głos zostaje na liście zawsze.
- Kontroler czyta `repo.settings.value` w chwili `open()` i `update { current -> }` przy zapisie, nie stan po `stateIn` (lekcja o `stateIn`).
- KDoc `SpeechSettings` mówi „restore default (AM-704) is a removal” — zgodne z planem; przy zmianach sprawdzić stare wyliczenia (lekcja o KDoc).
- Ustawienia zawierają szablony użytkownika: kontroler niczego nie loguje, błędy `VoiceCatalog` mają stałą kategorię bez wyjścia procesu (ENG-C8).
