# AM-812 · Dźwięk powiadomień (kanał SOUND)

Issue: #93 · Wymagania: FR-N1 (FR-N6, FR-N7 jako bramki) · docs/07 §Zdarzenia i kanały, docs/11 §4 · Etap: M7 · Zależy: AM-703

## Zakres

Kanał SOUND zaczyna grać: każde dostarczenie SOUND z `decide()` odtwarza krótki dźwięk systemowy macOS (`/usr/bin/afplay /System/Library/Sounds/<nazwa>.aiff`) przez `ProcessRunner`, tak jak `MacSayAdapter` uruchamia `say`. `DefaultNotificationCenter` rozdziela gałąź `SOUND, DOCK_BADGE -> Unit`: SOUND idzie do nowego `SoundNotifier`, DOCK_BADGE zostaje pusty (AM-903).

Bramki (już w `decide()` i centrum, bez zmian w polityce): macierz, profil projektu (`MUTED` i `ERRORS_ONLY` wycinają dźwięk jak inne kanały), cisza nocna i Skupienie (`SILENCED_IN_QUIET` ma już SOUND), wyciszona sesja (`manager.isMuted` w centrum). Dźwięk **gra także przy aktywnym oknie aplikacji** i nie zależy od mikrofonu (pytanie 3).

Kolumna „Dźwięk” w `ChannelMatrix`: po tym zadaniu działa, więc **nie oznaczamy jej** jako niedostępnej i nie zmieniamy `notifications:ui`. Kolumna „Dock” dalej nic nie robi — to AM-903, poza zakresem.

Nie robimy: wyboru dźwięku ani głośności w ustawieniach (pytanie 2), badge w Docku, portu w `notifications:api`, zmian w `core:process`.

Kolejność pracy w jednym PR (szacunek ok. 330 linii z testami): czyste rdzenie (`soundFor`, `SoundQueue`), adapter, notifier, spięcie w centrum i fabryce, poprawka `VoiceFlowTest`, docs/11, CHANGELOG `[Unreleased]`.

## Zmiany API

`notifications:api`: brak (port jest `internal` w `impl`, jak `SpeechPort`). Wariant pytania 1: w `NotificationSettings.defaultChannels` `TURN_ENDED -> setOf(POPUP, SOUND)`, `TERMINAL_BELL` bez zmian (rozdzielić gałąź `when`).

Typy w `impl` (wszystkie `internal`):

```kotlin
/** A short macOS system sound, a file `<fileName>.aiff` in `/System/Library/Sounds`. */
internal enum class SystemSound(val fileName: String) { GLASS("Glass"), PING("Ping"), BASSO("Basso"), HERO("Hero"), POP("Pop"), SUBMARINE("Submarine"), TINK("Tink") }

/** The sound of [kind]; fixed mapping (docs/07 has none, see question 2). */
internal fun soundFor(kind: NotificationKind): SystemSound

/** Why a sound was not played. */
internal sealed class SoundError {
    /** The player program does not exist or could not start. */
    internal data object Unavailable : SoundError()
    /** The player ended with [exitCode] other than 0, also after the fallback sound. */
    internal data class Failed(val exitCode: Int) : SoundError()
    /** The player ran longer than its timeout and was killed. */
    internal data object TimedOut : SoundError()
}

/** Port to the sound player. Plays to the end; cancelling the caller stops it. Never throws for player failures. */
internal interface SoundPort {
    suspend fun play(sound: SystemSound): Outcome<Unit, SoundError>
}

/**
 * [SoundPort] on macOS `afplay`, started through [runner] in [workDir] with argv `[program, <soundsDir>/<file>.aiff]`
 * and a 10 s timeout. A missing file makes `afplay` exit with a non-zero code; then one more try uses [FALLBACK]
 * (Glass), unless the sound already was the fallback.
 */
internal class AfplayAdapter(
    private val runner: ProcessRunner,
    private val workDir: Path,
    private val soundsDir: Path = Path.of("/System/Library/Sounds"),
    private val program: String = "/usr/bin/afplay",
) : SoundPort

/**
 * Pure reducer: at most one sound per cooldown (2 s, counted from the start of a play). During the cooldown one sound
 * waits; a more important kind replaces it ([importance]: FAILED > PERMISSION > NEEDS_INPUT > PULL_REQUEST >
 * TURN_ENDED > RUNNING_LONG > TERMINAL_BELL), a less or equally important one is dropped.
 */
internal data class SoundQueue(val cooling: Boolean = false, val pending: NotificationKind? = null) {
    fun offer(kind: NotificationKind): SoundStep
    fun cooldownEnded(): SoundStep
}
internal data class SoundStep(val state: SoundQueue, val play: NotificationKind?)

/**
 * Plays the deliveries of the sound channel through [sound], one after another in one consumer in [scope]; the
 * cooldown timer lives there too. Before a waiting sound plays after the cooldown it checks again that quiet hours
 * (FR-N6) did not start. A failure is logged as `warn("sound failed", "reason" to <category>)`, never the kind or path.
 */
internal class SoundNotifier(
    private val sound: SoundPort,
    private val settings: StateFlow<NotificationSettings>,
    private val scope: CoroutineScope,
    private val context: () -> DeliveryContext,
    private val logger: Logger,
) { fun offer(delivery: Delivery) /* never suspends */ }
```

Mapowanie (propozycja, pytanie 2): NEEDS_INPUT → Glass, PERMISSION → Ping, FAILED → Basso, TURN_ENDED → Hero, PULL_REQUEST → Pop, RUNNING_LONG → Submarine, TERMINAL_BELL → Tink.

`DefaultNotificationCenter`: nowy ostatni parametr `sound: (Delivery) -> Unit = {}`; `when`: `SOUND -> sound(delivery)`, `DOCK_BADGE -> Unit`. KDoc klasy wymienia dźwięk. Fabryka: `soundNotifier(process, settings, scope, context, logger)` obok `voiceNotifier`; `process == null` = ani głosu, ani dźwięku. Liczba parametrów fabryki bez zmian (10, istniejący `@Suppress`).

## Ryzyka i pytania

Pytanie blokujące (przed startem):

1. **Dźwięk po zakończeniu tury agenta (TURN_ENDED).** Człowiek nie słyszy sygnału po zakończeniu pracy agenta, bo docs/07 daje „Agent skończył turę” tylko popup, a popup w tle łatwo przeoczyć. Włączenie SOUND domyślnie zmienia domyślną macierz FR-N1 (`NotificationSettings.defaultChannels` w `notifications:api` i tabelę w docs/07). Dotyczy też użytkowników z zapisanym `notifications.json`: stary zapis trzymał kanały WSZYSTKICH rodzajów (zob. „Odstępstwa”), więc wymaga migracji. **Rekomendacja: tak** — TURN_ENDED = popup + dźwięk (Hero), bez głosu. Odpowiedź „nie” = `notifications:api` i tabela docs/07 bez zmian.

Pytania nieblokujące (plan przyjmuje rekomendację):

- **Pytanie 2: Zakres ustawień dźwięku.** Rekomendacja: w tym zadaniu tylko włączanie i wyłączanie w macierzy; stałe mapowanie rodzaj → dźwięk (wyżej) i głośność systemowa (bez `afplay -v`). Wybór dźwięku per rodzaj, głośność i odsłuch próbki to nowe pole w `NotificationSettings` (`api`), sekcja w `notifications.json` i kontrolki w `notifications:ui` — osobny wpis w roadmapie (FR-N1, moduły api/impl/ui).
- **Pytanie 3: Dźwięk przy aktywnym oknie aplikacji i przy mikrofonie.** Głos milknie przy aktywnym oknie (`onlyInBackground`). Rekomendacja: dźwięk gra zawsze (jest krótki, popup też się pokazuje, a przełącznik `onlyInBackground` jest opisany jako ustawienie głosu). Osobny przełącznik dla dźwięku wymagałby zmiany `api`.
- **Pytanie 4: Chłodzenie 2 s i priorytet.** Najwyżej jeden dźwięk na 2 s, jeden czeka (ważniejszy wypiera mniej ważny), reszta przepada; popup i głos niosą treść. Akceptujesz wartość 2 s?
- **Pytanie 5: Moduły względem roadmapy.** Plan nie wychodzi poza listę roadmapy: nie zmienia `notifications:ui` (kolumna „Dźwięk” działa po wdrożeniu), `app` zmienia tylko KDoc, `notifications:api` tylko przy pytaniu 1.

Ryzyka:

- Dźwięk i głos jednego zdarzenia grają naraz (`afplay` ok. 1 s, `say` startuje po ok. 0,2 s przez powłokę logowania). Akceptujemy; kolejkowanie głosu za dźwiękiem to osobna decyzja.
- `afplay` dla brakującego pliku: zakładamy kod ≠ 0 (stąd ponowna próba z Glass); potwierdzić ręcznie. Gdy Apple zmieni nazwy dźwięków, zostaje Glass, a przy jego braku tylko `warn`.
- Sesja wyciszona w czasie 2 s chłodzenia może jeszcze dostać czekający dźwięk (centrum sprawdza wyciszenie przy dostarczeniu, nie przy odtworzeniu); okno najwyżej 2 s.
- `VoiceFlowTest` i inne testy z `process = FakeProcessRunner` liczą wszystkie wywołania — trzeba je zawęzić do `say`, inaczej padną bez błędu w kodzie.
- Każdy dźwięk to proces powłoki logowania (`path_helper`); przy chłodzeniu 2 s najwyżej jeden proces naraz.
- Test „błąd nie blokuje następnego dźwięku” musi paść po usunięciu obsługi `Err` w konsumencie (lekcja o ścieżce błędu); sprawdzić mutacją.

## Odstępstwa od planu

- **Migracja `notifications.json` (schemat 1 do 2).** `NotificationSettingsSerializer.serialize` zapisywał kanały wszystkich rodzajów, więc każdy zapisany plik ma `"turnEnded": ["popup"]` i nowa domyślna by go nie objęła. Rozwiązanie w dwóch częściach: (a) `StoreSpec` ma `schemaVersion = 2` i `Migration(1)`, która usuwa `channels.turnEnded`, gdy jest zbiorem równym `{popup}` (stara domyślna; powtórzenia bez znaczenia); `["popup","voice"]`, `[]`, `["sound"]` i inne zostają jako świadome wybory; dane o nieoczekiwanym kształcie migracja zostawia, a serializer je odrzuca jak dotąd; (b) serializer zapisuje od schematu 2 tylko rodzaje różniące się od `defaultChannels`, więc kolejna zmiana domyślnej dotrze do wszystkich, którzy jej nie nadpisali. Plik nowszy niż schemat 2 dalej daje `NEWER_SCHEMA` (bez zapisu).
- **Ograniczenie:** świadomy wybór „tylko popup” sprzed migracji jest nie do odróżnienia od starej domyślnej i też dostaje dźwięk; użytkownik wyłącza go w macierzy (od tej chwili jest zapisany jako odstępstwo). Plik po migracji jest zapisywany od razu (`FileJsonStore`), a kopii schematu 1 nie ma.
- **Zmienione testy poza modułem impl (skutek nowej domyślnej):** `notifications:ui` (`NotificationDraftTest`, `NotificationSettingsDialogScreenTest`, `NotificationSettingsControllerTest`), `app` (`NotificationSettingsDialogWindowTest`), `notifications:api` testFixtures (`NotificationSettingsRepoContract`) i `NotificationSettingsTest`, `notifications:impl` (`ProjectPolicyTest`, `NotificationSettingsSerializerTest`, `NotificationPolicyTest`).
- **Testy, które trzeba było poprawić po zmianie domyślnej:** `NotificationPolicyTest` (`switching popups off…`: koniec tury bez popupu zostaje z samym SOUND) oraz `NotificationSettingsControllerTest` (fikstura `saved` używała `withChannel(TURN_ENDED, SOUND, true)`, które jest teraz wartością domyślną i znika przy zapisie; zamieniona na VOICE). Nowe: `NotificationSettingsMigrationTest`.
